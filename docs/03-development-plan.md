## 0. Разбор редакции 1: что было не так

Одиннадцать находок. Три из них меняют порядок итераций, две добавляют артефакты,
остальные уточняют критерии.

| # | Проблема ред. 1 | Почему это ошибка | Исправление |
|---|-----------------|-------------------|-------------|
| **1** | Оценки S/M/L в человеко-неделях | Разработку ведёт Claude, а не команда. Узкое место — **не скорость написания кода, а способность оператора проверить результат** и непрерывность между сессиями | Размер измеряется **временем проверки оператором**: каждая итерация проверяема за ≤ 15 минут по явному сценарию приёмки |
| **2** | Параллельные ветки после И-3 | Один исполнитель — параллелизм невозможен и вреден | Цепь строго линейна. Порядок оптимизируем не по параллельности, а по **раннему получению обратной связи** |
| **3** | И-1 (ядро) не даёт видимого результата | Оператор не может проверить измерительное ядро иначе как чтением кода. Это плохой DoD | **Ядро получает CLI как первого потребителя.** Проверяемо, скриптуемо, и это же — доказательство принципа «ядро без GUI» |
| **4** | Пресеты (И-3) проектировались, когда есть одна проба | Абстракция, выведенная из одного примера, почти наверняка не подойдёт HTTP- и DNS-пробам с другой формой параметров. Классическая ошибка преждевременного обобщения | **Правило трёх примеров**: сначала 6 разнотипных проб, потом обобщение в пресеты |
| **5** | Схема хранилища (И-2) до появления разных форм результатов | Та же ошибка. Схема `Sample/Result`, выведенная из ICMP, сломается на HTTP-waterfall и DNS-сравнении | Хранилище — после зоопарка проб. Специфика проб — в JSON-поле, общее — в колонках |
| **6** | Отчёты в конце (И-10) | Отчёт — заявленная ценность продукта, и его форма **диктует, какие метаданные надо сохранять**. Сделав в конце, обнаружим, что половины данных не сохранялось | **Минимальный отчёт рано (И-6).** Сквозной канал «измерение → PDF» существует с начала и тянет за собой требования к данным |
| **7** | Топология одной итерацией размера L | Самая большая и самая рискованная итерация неделима — плохо | Разделена: **И-9 граф только для чтения**, **И-10 редактор с `pin`**. Ценность раньше, риск ниже |
| **8** | Time-to-value < 60 с проверяется только в И-11 | Заявленное требование, проверяемое в самом конце, обычно оказывается невыполненным | Поток первого запуска входит в И-8 вместе с обнаружением |
| **9** | И-8 (агент) зависит от второй машины, которой нет | Итерация встанет в момент старта | Разделена: **И-12 протокол и функциональность** (проверяемо на VM), **И-13 валидация точности** (нужна физическая машина). Подготовка стенда — явный пункт |
| **10** | Автотест «ноль аллокаций» через `GC.CollectionCount` | Ненадёжно: коллекцию может вызвать посторонний код, тест будет мигать | Мерить `GC.GetAllocatedBytesForCurrentThread()` — дельту байт на поток, а не факт коллекции |
| **11** | Нет механизма непрерывности между сессиями | Разработку ведёт Claude в сессиях с ограниченным контекстом. Без живого состояния каждая сессия начинается с археологии | Введены **`STATUS.md`** (где мы, что дальше, какие решения приняты) и **`ARCHITECTURE.md`** (карта кода), обновляются в ритуале закрытия итерации |

## 1. Модель работы и что из неё следует

**Разработку ведёт Claude. Оператор принимает решения и проверяет результат.**

| Следствие | Что делаем |
|-----------|-----------|
| Узкое место — проверка, а не написание кода | Каждая итерация заканчивается **сценарием приёмки**: конкретные шаги, ≤ 15 минут, проверяются запуском, а не чтением диффа |
| Контекст сессии ограничен | `STATUS.md` и `ARCHITECTURE.md` — живые документы. Итерация не закрыта, пока они не обновлены |
| Регрессии некому заметить глазами | Тесты — не «хорошая практика», а **память проекта**. Архитектурные принципы оформляются падающими тестами |
| Нет издержек на синхронизацию между людьми | Итерации могут быть плотнее, но не длиннее — предел ставит проверяемость |
| Решения принимаются оператором | Каждая итерация с развилкой начинается с явного вопроса, а не с догадки |

## 2. Решения, зафиксированные планом

### 2.1 Лицензия — MIT

| Требование | Как MIT его закрывает |
|-----------|----------------------|
| Условие SignPath Foundation (бесплатная подпись) | OSI-одобренная ✅ |
| Совместимость с LGPL-плагином захвата | Разрешает зависимость при динамической линковке ✅ |
| QuestPDF Community | Open-source проекты покрыты ✅ |
| Атрибуция DB-IP Lite (CC BY-SA 4.0) | База — не производное кода; атрибуция в «О программе» ✅ |

Альтернатива Apache-2.0 (патентная оговорка) — для инструмента диагностики риск низкий.

### 2.2 `storm-agent`

| Аспект | Решение |
|--------|---------|
| Управляющий канал | TCP + TLS, порт по умолчанию `9737` |
| Каналы данных | TCP (throughput) и UDP (jitter/PDV/loss), порты согласуются в управляющем канале |
| Аутентификация | Pairing-токен, выдаётся оператором при сопряжении |
| Доверие | Самоподписанный сертификат + **pinning отпечатка** (модель SSH) |
| Обнаружение | mDNS в локальной сети + ручное добавление |
| Версионирование | Обмен версиями в рукопожатии **с первой версии**; несовместимость → внятная ошибка |

**Три режима одного бинаря:**
1. **Портативный** (`--once`) — ничего не устанавливает, живёт до закрытия. Основной сценарий выездной диагностики.
2. **Служба** (`--install-service`) — права нужны **только на установку**, работа их не требует (`R-01`).
3. **Встроенный** — GUI-клиент сам умеет быть агентом.

**Вне v1:** NAT-traversal и релеи. Агент должен быть достижим напрямую.

### 2.3 MVP — весь Уровень 0

Граница по §3 анализа: **Уровень 0 целиком, без SNMP и без плагина захвата.**
~80% ценности, работает без прав и без установки чего-либо, и это же правовая линия реза.

**Вне MVP:** SNMP, захват пакетов, Wi-Fi-анализ (`R-06` не проверен), SMB-throughput,
почтовая связность, RBL.

### 3.1 Зачем CLI

Не побочный продукт, а инструмент с четырьмя функциями:

1. **Делает ядро проверяемым** до появления GUI — оператор запускает команду и видит цифры.
2. **Доказывает принцип 8.2.2** («ядро без GUI») по построению: если CLI работает, ядро
   действительно не зависит от интерфейса. Это сильнее, чем правило в документе.
3. **Готовит server-вариант**: CLI и будущий сервер — два потребителя одного `Application`.
4. **Закрывает открытый вопрос ред. 1** «нужен ли CLI» — да, и он почти бесплатен.

### 3.2 Правила ссылок (проверяются тестами в `ArchTests`)

- `Domain` не ссылается ни на что.
- `Application` ссылается только на `Domain`.
- `App` и `Cli` **не ссылаются** на `Probes`, `Storage`, `Platform` — только через `Application` и DI.
- Ни один проект, кроме `plugins/`, не ссылается на SharpPcap.

Последнее правило одним движением решает изоляцию LGPL, работоспособность trimming
и принцип «опциональные зависимости только плагинами».

## 4. Ритуал завершения итерации

1. **Сценарий приёмки** — оператор выполняет шаги из DoD и видит результат. ≤ 15 минут.
2. **Баг-чекинг** — все тесты + граничные случаи: пустая сеть, недоступная цель,
   обрыв связи, отмена на середине, повторный запуск.
3. **Рефакторинг** — устранение дублирования и обходных путей. **Отдельным коммитом**,
   не смешанным с функциональностью.
4. **Проверка 12 архитектурных принципов** (§8.2 анализа). Особенно №8 (свой таймер),
   №9 (ноль аллокаций), №11 (плагины), №2 (ядро без GUI).
5. **Обновление `STATUS.md` и `ARCHITECTURE.md`.**

**Итерация не закрыта, пока приложение не запускается и не работает целиком.**
Каждая итерация — вертикальный срез, а не слой.

## 5. Цепочка итераций

### И-0 · Каркас и конвейер

Структура решения, `LICENSE`, анализаторы, `Directory.Build.props`. Базовые абстракции
домена: `Target`, `Probe`, `Sample`, `Result`, `Verdict`, `MeasurementContext`.
DI, логирование. Пустая оболочка CLI и пустое окно Avalonia. CI: сборка, тесты,
**воспроизводимая публикация** (условие SignPath). `STATUS.md`, `ARCHITECTURE.md`.

**Приёмка:** `dotnet publish` даёт самодостаточные single-file артефакты; `storm --help`
работает; окно запускается; `ArchTests` проходят.

> **Поправка к оценке размера.** В редакции 2 здесь стояло «≤ 15 МБ». Число было взято
> из консольного спайка (11.7 МБ) и к графическому клиенту отношения не имело.
> Фактически измерено при сборке И-0: **CLI — 13.1 МБ, GUI — 35.7 МБ** (обрезанный
> self-contained). Без обрезки GUI весит 97.4 МБ, поэтому обрезка включена,
> а несовместимая с ней встроенная поддержка COM — выключена.

### И-1 · Измерительное ядро + CLI 🔴 самая рискованная

`IHighResolutionClock` с **калибровкой loopback-базиса** при старте. `IcmpProbe`:
серии echo, поток сэмплов, отмена; агрегация RTT (min/avg/max/stddev/перцентили), loss,
**jitter по RFC 3550**, PDV. Определение интерфейсов и **их типа** (физический /
виртуальный / VPN / Wi-Fi). `MeasurementContext`. Горячий путь без аллокаций.

**Приёмка:**
```bash
storm ping 192.168.200.1 --count 300 --interval 20ms
```
- Цифры воспроизводят [spike-01](../spikes/spike-01-icmp-timing) на том же стенде
- В выводе видно **предупреждение о виртуальном адаптере** (стенд на Hyper-V)
- Автотест: шум стека ≤ 20% измеряемой величины — **падает**, если нарушено
- Автотест: 1000 проб не увеличивают `GC.GetAllocatedBytesForCurrentThread()` сверх порога
- Автотест: `PingReply.RoundtripTime` нигде не попадает в `Result`

> Первой — потому что ошибка здесь расползётся по всему продукту и всплывёт на боевых
> тестах, когда переделывать дорого.

---

### И-2 · Зоопарк проб

Правило трёх примеров: обобщать можно только то, у чего есть несколько разных реализаций.

Пробы TCP-connect, UDP, DNS-query, HTTP(S), TLS. Traceroute по TTL. Единый `IProbe`
с декларацией параметров. Все — через CLI.

**Приёмка:** шесть команд (`storm tcp`, `storm dns`, `storm http`, `storm tls`,
`storm trace`, `storm ping`) дают осмысленный вывод; формы результатов заметно разные —
и это видно в выводе.

---

### И-3 · Хранилище и журнал прогонов

Теперь схема выводится из шести разнотипных результатов, а не из одного.

SQLite: `Target/Run/Result/Sample` + агрегаты по бакетам. Общее — в колонках,
специфика пробы — в JSON-поле. **Retention и downsampling с первого дня** (`R-14`).
Оркестратор прогонов: параллельность, отмена, **инкрементальное сохранение**.

**Приёмка:** `storm ping ... --save` → `storm runs list` → `storm runs show <id>`
показывает сырые сэмплы; прерванный на середине прогон сохранил измеренное.

### И-4 · GUI-каркас и первый экран

Оболочка навигации Avalonia. Экран `/local/tests/latency`: ping-монитор с живым графиком
ScottPlot. **Run Drawer.** **Status Bar с типом активного адаптера и предупреждением**
о vSwitch/VPN. Дашборд-заглушка.

**Приёмка:** запустил монитор → живой график → закрыл приложение → открыл → история на месте.
Предупреждение о виртуальном адаптере видно на стенде.

### И-5 · Пресеты и сквозная триада

Абстракция выводится из реальных данных шести проб.

CRUD пресетов, версионирование, теги, поиск, импорт/экспорт JSON. `/presets`, `/runs`,
`/runs/{id}`. Действие **«Сохранить как пресет»** на экране результата.

**Приёмка:** тест → пресет → повторный запуск из библиотеки → результат в журнале →
экспорт → импорт даёт тот же прогон.

### И-6 · Минимальный отчёт

Рано и намеренно: канал «измерение → PDF» должен существовать до того, как накопится
масса измерений, иначе окажется, что нужных метаданных не сохранялось.

`IReportRenderer` → QuestPDF. Одностраничный отчёт: заголовок, один график,
таблица агрегатов, **указание методики** (RFC 3550), **секция «Условия измерения»**
(интерфейс, тип, калибровка, версия).

**Приёмка:** прогон → «Сохранить в PDF» → открывается читаемый документ, в котором
указано, чем и в каких условиях мерили. Подмена рендерера на заглушку не требует
правок вне `Reporting`.

> Спайк-06 (качество вёрстки QuestPDF) выполняется внутри этой итерации, а не до неё —
> она сама по себе достаточно мала.

---

### И-7 · Traceroute и непрерывный MTR

Дифференциатор — рано, а не в хвосте. Планка PingPlotter (`R-17`).

Непрерывный MTR: loss и latency **по каждому хопу**, история во времени. MOS по хопам
(G.107). Аннотация хопов: reverse DNS, ASN — офлайн-база **DB-IP Lite** + атрибуция.
Детект смены маршрута, сравнение трасс, определение точки деградации.

**Приёмка:** непрерывный MTR к внешнему узлу; таблица хопов с loss/latency/MOS;
через час видно, менялся ли маршрут; отчёт показывает, на каком хопе и в какой AS
начинаются потери.

---

### И-8 · Обнаружение, инвентарь и первый запуск

Ping-sweep с ограничением параллелизма + `SendARP` + `GetIpNetTable`. Обогащение:
OUI-вендор, reverse DNS, NetBIOS, mDNS, SSDP, WS-Discovery. Модель `Evidence`
с источником, временем и достоверностью. `/local/discovery` (подтверждение диапазона,
rate-limit, аудит), `/local/devices`, карточка устройства, **diff между сканами**.
**Поток первого запуска** — здесь, а не в конце.

**Приёмка:** чистый профиль → первый запуск → карта устройств **менее чем за минуту**
без чтения документации; /24 инвентаризуется ≤ 5 с (эталон: 1.55 с); MAC у всех живых;
повторный скан показывает изменения; активные действия в журнале аудита.

---

### И-9 · Топология: чтение

Построение графа из `Evidence`, слияние с оценкой достоверности. Топология L3:
подсети, маршрутизаторы, traceroute, таблица маршрутизации. `AvaloniaGraphControl`
+ MSAGL для авто-раскладки. **Визуальное различение достоверности** (L-46).
Экспорт PNG/SVG/JSON.

**Приёмка:** карта строится автоматически; связь, выведенная эвристикой, визуально
отличима от подтверждённой; граф на 300 узлах остаётся отзывчивым.

> Спайк-04 (граф 300 узлов) — **до** этой итерации. При провале готовых компонентов
> переходим на собственный рендер поверх Skia, и это меняет объём.

---

### И-10 · Топология: редактор

`Nodify.Avalonia` для правки. Переименование, тип устройства, добавление и удаление
связей, объединение дублей. **`pin`** правок оператора.

**Приёмка:** правка оператора переживает три последовательных рескана; объединённые
дубли не расходятся обратно.

---

### И-11 · Внешние пробы: сценарии и инспекторы

Конструктор probe-сценариев, мульти-таргет, шаблонные наборы целей. Синтетическая
транзакция: DNS → TCP → TLS → HTTP → проверка контента. HTTP-инспектор с разбивкой
тайминга (waterfall), DNS-инспектор (сравнение резолверов, DNSSEC), TLS-инспектор.
Внешний IP/ASN/PTR, STUN/тип NAT, IPv6-готовность.

**Приёмка:** сценарий из цепочки шагов даёт разбивку по фазам; пять резолверов
сравниваются в одной таблице.

---

### И-12 · Агент: протокол и функциональность

Проверяемо на виртуальной машине — физическая не нужна.

`StormMachine.Protocol`: контракты, версионирование рукопожатия. `storm-agent`:
TLS, pairing-токен, pinning отпечатка, mDNS-обнаружение, три режима запуска.
TCP-throughput: N потоков, прогрев, отбрасывание разгона (RFC 6349). UDP с **гибридным
spin-wait pacing**, loss, out-of-order.

**Приёмка:** сопряжение клиента и агента на VM; повторное подключение не требует
подтверждения (pinning работает); подмена сертификата вызывает явную ошибку;
агент в портативном режиме не требует установки и прав.

> Спайк-05 (рукопожатие и pacing) — до этой итерации.

---

### И-13 · Валидация точности и качество канала 🔬 нужна физическая машина

**Явное условие: к началу итерации подготовлена вторая физическая машина в той же сети.**
Без неё измерения пойдут через vSwitch — тот самый шум, что дал p99 в 18× выше p50.

Jitter, PDV, MOS/R-фактор (G.107), bufferbloat (оценка A–F). Speedtest через NDT7
с **отображением используемого бэкенда**. Совместимость как клиент с `iperf3 -s`.

**Приёмка:** замер между двумя физическими машинами; результат сходится с `iperf3`
в пределах разумного расхождения; джиттер на заведомо чистом канале не превышает шумовой пол.

---

### И-14 · Планировщик, мониторы, алерты

Quartz.NET с persistent store: разово, интервал, cron, окна обслуживания. **Политика
misfire** для сна, выключения, перезагрузки. `/monitors`: uptime %, SLA/SLO, бюджет
ошибок. Алерты: пороги с гистерезисом, каналы (трей, звук, e-mail, webhook).

**Приёмка:** расписание переживает перезапуск приложения и уход машины в сон;
алерт срабатывает по порогу и не «дребезжит» на границе.

---

### И-15 · Отчёты: полный набор

Наращивание И-6. Шаблоны: Executive summary, Технический, Акт приёмки, SLA.
Графики, таблицы, схема топологии. **Baseline**: фиксация эталона и сравнение
«было / стало». Экспорт CSV/JSON/PNG.

**Приёмка:** PDF «Акт тестирования» с топологией, графиками, методиками и условиями;
сравнение с baseline показывает изменения.

### И-16 · Полировка MVP 🏁

Экран `/settings/capabilities` с честной картиной уровней. Профили сетевого окружения,
`/settings/*` целиком. Command Palette (`Ctrl+K`), Quick Target, Notification Center.
Локализация RU/EN. Учётные данные в DPAPI. Velopack, **подпись через SignPath Foundation**,
авто-обновление.

**Приёмка:** чистая машина → установка → первый запуск → карта сети за минуту.
Подписанный инсталлятор не вызывает предупреждения SmartScreen после набора репутации.

**Здесь MVP заканчивается.**

### И-17 · Уровень 1: SNMP

SharpSnmpLib, v1/v2c/v3, учётные данные в DPAPI. `ifTable`, счётчики ошибок и утилизации,
`sysDescr`. **LLDP-MIB** → связи L2, **BRIDGE-MIB FDB** → привязка устройства к порту.
Повышение достоверности связей топологии при наличии SNMP.

**Приёмка:** при наличии SNMP топология показывает порты свитчей; при отсутствии —
деградирует явно, без ложной уверенности.

---

### И-18 · Уровень 2: плагин захвата

`ICaptureProvider` в `Application`, реализация — в `plugins/`. **Детект установленного
Npcap** (никакой установки из нашего инсталлятора). LLDP/CDP-кадры, пассивный анализ,
детект rogue DHCP по broadcast, пассивный OS-fingerprint.

**Приёмка:** без Npcap приложение работает полностью и честно сообщает, чего не хватает;
с Npcap функции появляются; `plugins/` — единственное место со ссылкой на SharpPcap.

---

### И-19 · Масштабный рефакторинг и баг-чекинг

Отдельная итерация по требованию оператора — не «когда будет время».

Сквозной разбор долга. Проверка 12 принципов по всему коду. Ревизия покрытия тестами.
Нагрузочный прогон: 4096 узлов, ряды за год. **Проверка готовности к server-варианту:**
сможет ли `Application` работать за сетевым API без правок домена. Профилирование.

## 6. Обоснование порядка

| Принцип | Как применён |
|---------|--------------|
| **Риск — вперёд** | И-1 (точность) — первая содержательная. И-9 (граф) — до наращивания функций поверх топологии |
| **Проверяемость на каждом шаге** | CLI появляется в И-1, GUI в И-4. Оператор видит результат с первой итерации, а не с четвёртой |
| **Три примера до абстракции** | Зоопарк проб (И-2) → хранилище (И-3) → пресеты (И-5). Ни одна абстракция не выводится из одного случая |
| **Сквозной канал до артефакта — рано** | Минимальный PDF в И-6 задаёт требования к метаданным, пока их дёшево менять |
| **Дифференциатор в середине** | MTR (И-7) и топология (И-9, И-10) — то, чем отличаемся, — не в хвосте |
| **Внешние зависимости — поздно и изолированно** | Физическая вторая машина нужна только к И-13; SNMP и Npcap — после MVP |
| **Уровни как линия реза** | MVP = Уровень 0 (И-0…И-16). Уровни 1 и 2 после, их отсутствие продукт не ломает |

**Цепь строго линейна** — один исполнитель. Единственная свобода: порядок И-7, И-8 и И-11
между собой можно менять без ущерба.
