**1. Эмпирические spike-программы** — три консольных приложения на .NET 8, запущенные

| Spike | Что проверял |
|-------|--------------|
| [`spike-01-icmp-timing`](../spikes/spike-01-icmp-timing) | ICMP без admin, разрешающая способность RTT, шум таймера, TTL, PMTU, ping-sweep /24 |

## 2. Результаты по каждому вопросу

### 🟢 R-01 — ICMP без прав администратора: ПОДТВЕРЖДЕНО, и даже больше

Работает **всё** без admin:

```
ttl= 2  TtlExpired    31.28.6.1          1.092 мс
ttl= 3  TtlExpired    10.10.13.181       0.953 мс
ttl= 6  Success       1.1.1.1           39.419 мс     ← traceroute отработал
Максимальный payload с DF: 1472 байт → PMTU ≈ 1500    ← PMTU отработал
```

**Неожиданный результат:** raw-сокет ICMP тоже создаётся, отправляет и принимает без admin:

```
SendTo вернул 40 байт — отправка прошла
Получено 60 байт от 192.168.200.1, ICMP type=0, id=11696 (наш id=11696)
✔ RAW ICMP ПОЛНОСТЬЮ РАБОТАЕТ БЕЗ ADMIN
```

**Но у raw есть предел.** Параллельный traceroute (12 сокетов с разными TTL одним залпом)
**провалился** — ICMP Time Exceeded не дошёл ни до одного сокета:

```
ttl= 1..5   *          ← хопы потеряны
ttl= 6   1.1.1.1  32.807 мс
```

Тогда как `IcmpSendEcho2` те же хопы вернул корректно.

**Решение:** гибрид. `IcmpSendEcho2` — основной путь (traceroute, PMTU, надёжность).
Raw-сокет — опциональный режим для высокочастотных серий echo, где нужен свой ID/seq
и корреляция ответов. Raw **не** является обязательным.

### 🔴 R-10 — Точность таймингов: ГЛАВНАЯ НАХОДКА ЭТАПА

**Проблема, которую мы бы не заметили без замера.** `PingReply.RoundtripTime` — целое число
миллисекунд (`IcmpSendEcho2` возвращает `DWORD` в мс):

```
API RoundtripTime : min 0.000 avg 0.100 max 5.000 мс
  → различимых значений RTT в выборке из 300: 6  (0, 1, 2, 3, 4, 5)
Stopwatch         : min 0.400 avg 0.639 p95 0.878 max 5.804 мс
  → различимых значений: 285
```

В локальной сети, где RTT < 1 мс, API округляет почти всё в 0. **Джиттер, PDV и MOS,
посчитанные по `RoundtripTime`, будут мусором.**

Что показал `Stopwatch`:

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Разрешение таймера | 100 нс (10 МГц) | `Stopwatch.IsHighResolution = true` |
| Стоимость чтения таймера | медиана 0 мкс, p99 0.1 мкс | Ничтожна |
| Пол накладных расходов (loopback ping) | 0.27 мс | Систематическая добавка — вычитается калибровкой |
| Timestamp в пакете vs код вокруг вызова | разница **0.002 мс** | Усложнять незачем |
| **GC за 300 замеров** | **0 коллекций, 0 мс пауз** | Главный страх не подтвердился |
| **Собственный джиттер UDP-стека (RFC 3550)** | **0.008 мс** | При измерении джиттера 1 мс это 0.8% |

**Требование §6 (шум стека ≤ 20% измеряемой величины) выполнено с запасом ~25×.**
.NET проходит. Условие: не аллоцировать в горячем пути (переиспользуемые буферы, без LINQ).

**Темповка пакетов** (нужна для UDP-jitter и throughput, цель — интервал 1.000 мс):

```
Thread.Sleep(1)                     : p50 0.994  p95 1.511  max 1.670 мс ошибки
Thread.Sleep(1) + timeBeginPeriod(1): p50 0.998  p95 1.516  max 1.969 мс  ← НЕ ПОМОГАЕТ
SpinWait (жжём CPU)                 : p50 0.000  p95 0.001  max 0.433 мс
Гибрид Sleep(0)+SpinWait            : p50 0.000  p95 0.001  max 0.189 мс  ← выбор
```

`Thread.Sleep(1)` спит вдвое дольше запрошенного, а `timeBeginPeriod(1)` этого не чинит
(с Windows 10 2004 он влияет только на процесс и не возвращает старое глобальное поведение).
Значит **генератор пакетов должен работать на гибридном spin-wait в выделенном потоке** —
и это осознанно жжёт ядро CPU на время теста.

### 🟢 R-02 — Npcap: БЛОКЕР СНЯТ ОБХОДНЫМ ПУТЁМ

**Лицензионная картина (🔴 требует юридической проверки):**

- Бесплатная лицензия Npcap — **только 5 установок**, распространение **запрещено**,
  silent-инсталлятора нет (он только в OEM-версии).
- **Npcap OEM Redistribution** — платная. Цены публично не раскрыты: четыре тарифа
  по размеру компании, разовый выкуп + опциональная годовая поддержка, обращение в sales.
- **SharpPcap и PacketDotNet — LGPL-3.0.** Для закрытого продукта это означает: только
  динамическая линковка отдельными сборками, **запрет на ILMerge/статическую линковку**,
  публикация уведомления и возможность подмены DLL пользователем. Это **конфликтует
  с single-file/trimmed publish** — придётся исключать эти сборки из упаковки.

**Но главное — L2-инвентаризация оказалась возможна вообще без Npcap:**

```
A. SendARP (IPHLPAPI) — резолв IP→MAC БЕЗ Npcap и БЕЗ admin
   Шлюз 192.168.200.1 → MAC 00:00:5E:00:01:C8  (2.262 мс)  ✔ РАБОТАЕТ

B. GetIpNetTable — ARP-кэш ОС целиком: 332 записи

C. ИНВЕНТАРИЗАЦИЯ /24 БЕЗ ДРАЙВЕРА
   Живых узлов: 45 (ping-sweep 0.217 с)
   MAC получен для: 45 из 45 (SendARP 1.331 с)
   ИТОГО: 1.548 с, БЕЗ драйвера и БЕЗ admin
```

45 из 45 — стопроцентное покрытие. Плюс OUI → вендор, то есть тип устройства
угадывается уже на этом уровне.

**Что реально остаётся за Npcap:**

| Функция | Есть ли обход |
|---------|---------------|
| Приём LLDP/CDP-кадров | ✅ Да — через SNMP LLDP-MIB (см. R-05) |
| Пассивный анализ трафика | ❌ Нет |
| Детект rogue DHCP по broadcast | ⚠️ Частично — активным DHCP-запросом |
| Пассивный OS-fingerprint | ❌ Нет |
| Инжекция произвольных L2-кадров | ❌ Нет |

**Рекомендация: Npcap — опциональный плагин, а не зависимость ядра.**
Продукт полноценен без него. С ним получает пассивный анализ. Это снимает разом
лицензионный риск, риск UX первого запуска и риск конфликта LGPL с упаковкой.

Есть ещё **LLTD** (Link Layer Topology Discovery, `[MS-LLTD]`) — родной протокол Windows,
которым строится системная «Карта сети». Спецификация открыта. Работает только внутри
одной подсети (не маршрутизируется). Как дополнительный источник Evidence — интересен,
но нестандартен вне Windows-мира; в бэклог, не в v1.

### 🟡 R-05 — LLDP/CDP: работает, но покрытие неполное

Через SNMP LLDP-MIB (`lldpRemTable`) — стандартный путь, Npcap не нужен. Ограничения,
подтверждённые источниками:

- LLDP не реализован в дешёвых и неуправляемых свитчах.
- **Неуправляемый свитч или хаб между инструментом и управляемым свитчем ломает топологию** —
  инструмент показывает неверную связность.
- ПК, принтеры, IoT-устройства себя не анонсируют — LLDP/CDP покрывает только сетевое
  оборудование и отдельные серверы.

**Это прямое подтверждение правильности модели Evidence из §2 анализа.** LLDP — источник
высокой достоверности там, где он есть; всё остальное достраивается эвристиками
с честно пониженной уверенностью. Показывать «уверенную» топологию там, где её нет, нельзя.

### 🟢 R-14 — Хранилище: SQLite достаточно

SQLite тянет временные ряды при двух условиях: **downsampling и retention обязательны,
а не опциональны.** Схема: сырые сэмплы с горизонтом (например, 90 дней) + таблица
агрегатов по бакетам `(series_id, bucket_ts)` с `count/min/max/avg` для истории.

DuckDB (колоночный, в 10–50 раз быстрее на агрегатах) — **не в v1.** Появится, если
отчёты за год начнут тормозить.

### 🔴 R-16 — Подпись и EDR: правила изменились

Два факта, меняющих план:

1. **С марта 2024 EV-сертификаты больше не дают мгновенного доверия SmartScreen.**
   Репутация набирается объёмом загрузок одинаково для OV и EV.
2. **С 1 марта 2026 максимальный срок действия сертификата подписи кода — 458 дней.**

Цены (2026): OV — от ~$225/год, EV — от ~$279/год.

**Рекомендация: брать OV** — дешевле, а на SmartScreen влияет так же. И принять как
данность **период низкой репутации** в начале жизни продукта: первые пользователи
будут видеть предупреждение. Отдельно готовить пакет документов для служб ИБ заказчиков
(мы делаем сканер портов — это будет вызывать вопросы).

### 🟢 R-17 — Конкуренты: ниша есть

| Продукт | Сильная сторона | Слабость для нашей ниши |
|---------|-----------------|--------------------------|
| **PingPlotter** | Эталон непрерывного traceroute: графики latency/loss/jitter **по хопам**, MOS на хоп, история, отчёты для споров с провайдером | Только путь. Ни топологии, ни инвентаря, ни локальных тестов |
| Domotz | Облачный MSP-инструмент, мультисайт, удалённые действия | Облако и подписка; не автономен |
| LanSweeper | Глубокая инвентаризация активов, ПО, лицензий | Слаб в реальном времени и в топологии |
| Advanced IP Scanner | Мгновенный старт, бесплатен | Только сканер |

**Ниша Storm Machine:** связка **«топология + локальная диагностика + внешние пробы +
пресеты + расписание + отчёт»** в одном автономном настольном инструменте без облака.
Ни один из перечисленных не закрывает всю цепочку.

Планка, которую надо взять как минимум: непрерывный traceroute уровня PingPlotter.
Это не «дополнительная фича», а то, по чему нас будут сравнивать.

### 🟢 R-18 — Методики: на что ссылаться

| Стандарт | Что даёт |
|----------|----------|
| RFC 3550 §6.4.1 | Формула interarrival jitter — уже реализована в spike-01 |
| **RFC 6349** | Framework for TCP Throughput Testing — методика, дающая повторяемые результаты между площадками |
| ITU-T Y.1564 | Активация Ethernet-сервиса, полная валидация SLA одним тестом. ⚠️ Разрушающий тест — только когда сервисы не работают |
| ITU-T G.107 | E-model → R-фактор → MOS |

**Требование к отчётам:** у каждого измерения в PDF указывать методику. Отчёт со ссылкой
на RFC 6349 — аргумент в споре с провайдером; отчёт без методики — просто картинка.

### 🟢 R-19 — Упаковка: замерено

| Режим публикации | Размер |
|------------------|--------|
| Framework-dependent | **0.2 МБ** (нужен установленный .NET) |
| Self-contained, single-file, trimmed | **11.7 МБ** |
| NativeAOT | ❌ **не собрался**: `Platform linker not found` — требует workload «Desktop development with C++» в Visual Studio |

NativeAOT добавляет зависимость сборочной среды от C++ toolchain и плохо уживается
с рефлексией. Для v1 не нужен — **берём self-contained single-file**.

11.7 МБ для полностью автономного приложения — отлично (для сравнения, Electron-приложение
начинается со ~150 МБ). **Оговорка:** trimming несовместим с LGPL-сборками SharpPcap —
ещё один аргумент выносить Npcap-функционал в отдельный опциональный плагин.

**Velopack** — преемник Squirrel: дельта-обновления, кроссплатформенность, сборка одной
командой, автомиграция со Squirrel. Рекомендация для авто-апдейта. Inno Setup — запасной
вариант для «классического» инсталлятора без апдейтера.

### 🟢 R-20 — Server-вариант: правило подтверждено

### 🟢 R-21 — Раскладка графа: готовые компоненты проходят, но не любые

**Спайк-04** ([spikes/spike-04-graph](../spikes/spike-04-graph)), выполнен перед И-9,
как требует план. Проверялся движок MSAGL (`AutomaticGraphLayout` 1.1.12) — тот самый,
что `AvaloniaGraphControl` несёт внутри себя. Обе библиотеки под MIT, к нашей лицензии
претензий нет.

Граф брался формы настоящей сети: несколько маршрутизаторов, десяток коммутаторов,
остальное — конечные узлы. Случайный граф той же плотности раскладывается иначе,
и мерить на нём значило бы мерить не то.

| Узлов | Ярусная (Sugiyama) | Полотно | По расстояниям (MDS) | Полотно |
|-------|--------------------|---------|----------------------|---------|
| 36    | 32 мс              | 15.6 : 1 | 16 мс               | 1.3 : 1 |
| 91    | 135 мс             | 27.3 : 1 | 63 мс               | 1.3 : 1 |
| **300** | **280 мс**       | **64.8 : 1** | **361 мс**      | **1.7 : 1** |
| 609   | 426 мс             | 108 : 1  | 1073 мс             | 1.3 : 1 |
| 1026  | 739 мс             | 158 : 1  | 2610 мс             | 1.5 : 1 |

**По времени порог пройден с запасом**: 300 узлов раскладываются за треть секунды при
бюджете в секунду, память — 26 МБ. Собственный рендер поверх Skia не нужен, объём И-9
остаётся плановым.

**Но спайк нашёл второй порог, которого в плане не было — вытянутость полотна.**
Ярусная раскладка для сети из 300 узлов даёт полотно 32517 × 502 точки, то есть
**65 : 1**. Формально это успех: быстро и корректно. На деле — не карта, а список,
выложенный в строку, по которому нужно скроллить горизонтально минуту. Причина в форме
данных: у сети мало уровней и очень много листьев, а ярусная раскладка кладёт каждый
уровень в ряд.

**Три следствия для И-9:**

1. **Раскладка по расстояниям, а не ярусная.** MDS держит соотношение сторон около
   1.5 : 1 на всех размерах. Ярусная останется — но для другого вопроса: путь
   трассировки это направленная цепочка, и там она как раз уместна.
2. **Потолок MDS — примерно 500 узлов на секунду.** Дальше время растёт быстрее
   линейного: 609 узлов — 1.1 с, 1026 — 2.6 с.
3. **Конечные узлы сворачиваются в счётчик на коммутаторе.** Свёрнутая форма
   (только структура) раскладывается за 5–36 мс, и триста отдельных прямоугольников
   с адресами всё равно не карта. Разворачивать — по требованию.

## 3. НОВОЕ: риски, которых не было в анализе

### 3.1 🔴 Виртуальные адаптеры и VPN искажают измерения

Обнаружено эмпирически. На стенде (Hyper-V vSwitch):

```
Обычный приоритет : p50 0.496  p95 0.881  p99 8.915  max 10.362 мс
High + timeBeginPeriod: p50 0.474  p95 0.786  p99 11.303  max 11.540 мс
```

p99 в **18 раз** выше p50. Повышение приоритета процесса и потока **не помогло** —
стало даже хуже. Источник выбросов не наш код и не GC (0 пауз), а виртуальный коммутатор.

**Следствие — новое требование:** продукт обязан определять тип адаптера (физический /
виртуальный / VPN / Wi-Fi) и **предупреждать оператора**, что измерения через vSwitch или VPN
содержат собственный шум. Иначе пользователь припишет джиттер гипервизора своей сети.
Это же — повод добавить в отчёт секцию «условия измерения».

### 3.2 🔴 QuestPDF не подходит части заказчиков

Публичные компании и госсектор не подпадают под Community-лицензию **независимо от выручки**.
Если целевой рынок включает госзаказчиков — либо платная лицензия сразу, либо PDFsharp.
Отсюда требование изолировать генератор отчётов за интерфейсом.

### 3.3 🟡 LGPL SharpPcap конфликтует с упаковкой

Trimming и single-file publish несовместимы с требованиями LGPL к возможности подмены
библиотеки. Ещё один довод за вынесение Npcap-функционала в отдельный плагин,
загружаемый отдельной сборкой.

### 3.4 🟡 Период низкой репутации у SmartScreen неизбежен

EV больше не решает проблему. Первые сотни пользователей увидят предупреждение
независимо от того, сколько мы заплатим за сертификат.

## 3.5 ДОПОЛНЕНИЕ: продукт открытый — что это меняет

Решение оператора об open-source (принято после первой сдачи отчёта) потребовало
доисследования трёх пунктов.

| Пункт | Было | Стало |
|-------|------|-------|
| **QuestPDF** | 🔴 Риск: не для публичных компаний и госсектора | 🟢 **Снят.** Community-лицензия прямо покрывает open-source проекты |
| **Подпись кода** | 🔴 OV ~$225/год + период низкой репутации | 🟢 **SignPath Foundation — бесплатная OV-подпись для OSS.** Условия: OSI-одобренная лицензия, публичный репозиторий, воспроизводимая сборка из него, активная поддержка. ⚠️ Издателем в SmartScreen будет значиться «SignPath Foundation», а не мы |
| **SharpPcap LGPL-3.0** | 🟡 Ограничения на линковку в закрытом продукте | 🟢 Проблема совместимости снята. Техническое ограничение на trimming остаётся |
| **Npcap** | Предполагалось: OEM-лицензия за деньги | 🔴 **Хуже, чем думали.** NPSL основана на GPLv2, но **не является open-source** и запрещает распространение без отдельного разрешения. У Wireshark для этого именное исключение; для других OSS-проектов разрешение запрашивается индивидуально |

**Ключевой вывод по Npcap:** открытость нашего кода **не даёт** права его распространять.
Значит подтверждается решение §2 `R-02`: **Npcap не входит в дистрибутив ни в каком виде.**
Продукт детектирует уже установленный драйвер; установку выполняет пользователь сам
с официального сайта. Это одновременно и правовое, и UX-решение.

**Новое требование, вытекающее из условий SignPath:** сборка релиза должна быть
воспроизводима из публичного репозитория. Это влияет на CI и на процесс релиза —
учесть в плане Этапа 4.

**Новое решение к принятию:** конкретная лицензия проекта. Должна быть OSI-одобренной
(условие SignPath) и совместимой с LGPL-плагином захвата. Рекомендация — **MIT**.

Источники: [Nmap/Npcap Legal Notices](https://nmap.org/book/man-legal.html) ·
[SignPath Foundation — условия для OSS](https://signpath.org/terms.html) ·
[SignPath для open source](https://signpath.io/solutions/open-source-community)
