## 2. Результаты по каждому вопросу

### 🟢 R-01 — ICMP без прав администратора: ПОДТВЕРЖДЕНО, и даже больше

Работает **всё** без admin:

```
ttl= 2  TtlExpired    31.28.6.1          1.092 мс
ttl= 3  TtlExpired    10.10.13.181       0.953 мс
ttl= 6  Success       1.1.1.1           39.419 мс     ← traceroute отработал
Максимальный payload с DF: 1472 байт → PMTU ≈ 1500    ← PMTU отработал
```

**Неожиданный результат:** raw-сокет ICMP тоже создаётся, отправляет и принимает без admin:

```
SendTo вернул 40 байт — отправка прошла
Получено 60 байт от 192.168.200.1, ICMP type=0, id=11696 (наш id=11696)
✔ RAW ICMP ПОЛНОСТЬЮ РАБОТАЕТ БЕЗ ADMIN
```

**Но у raw есть предел.** Параллельный traceroute (12 сокетов с разными TTL одним залпом)
**провалился** — ICMP Time Exceeded не дошёл ни до одного сокета:

```
ttl= 1..5   *          ← хопы потеряны
ttl= 6   1.1.1.1  32.807 мс
```

Тогда как `IcmpSendEcho2` те же хопы вернул корректно.

**Решение:** гибрид. `IcmpSendEcho2` — основной путь (traceroute, PMTU, надёжность).
Raw-сокет — опциональный режим для высокочастотных серий echo, где нужен свой ID/seq
и корреляция ответов. Raw **не** является обязательным.

### 🔴 R-10 — Точность таймингов: ГЛАВНАЯ НАХОДКА ЭТАПА

**Проблема, которую мы бы не заметили без замера.** `PingReply.RoundtripTime` — целое число
миллисекунд (`IcmpSendEcho2` возвращает `DWORD` в мс):

```
API RoundtripTime : min 0.000 avg 0.100 max 5.000 мс
  → различимых значений RTT в выборке из 300: 6  (0, 1, 2, 3, 4, 5)
Stopwatch         : min 0.400 avg 0.639 p95 0.878 max 5.804 мс
  → различимых значений: 285
```

В локальной сети, где RTT < 1 мс, API округляет почти всё в 0. **Джиттер, PDV и MOS,
посчитанные по `RoundtripTime`, будут мусором.**

Что показал `Stopwatch`:

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Разрешение таймера | 100 нс (10 МГц) | `Stopwatch.IsHighResolution = true` |
| Стоимость чтения таймера | медиана 0 мкс, p99 0.1 мкс | Ничтожна |
| Пол накладных расходов (loopback ping) | 0.27 мс | Систематическая добавка — вычитается калибровкой |
| Timestamp в пакете vs код вокруг вызова | разница **0.002 мс** | Усложнять незачем |
| **GC за 300 замеров** | **0 коллекций, 0 мс пауз** | Главный страх не подтвердился |
| **Собственный джиттер UDP-стека (RFC 3550)** | **0.008 мс** | При измерении джиттера 1 мс это 0.8% |

**Требование §6 (шум стека ≤ 20% измеряемой величины) выполнено с запасом ~25×.**
.NET проходит. Условие: не аллоцировать в горячем пути (переиспользуемые буферы, без LINQ).

**Темповка пакетов** (нужна для UDP-jitter и throughput, цель — интервал 1.000 мс):

```
Thread.Sleep(1)                     : p50 0.994  p95 1.511  max 1.670 мс ошибки
Thread.Sleep(1) + timeBeginPeriod(1): p50 0.998  p95 1.516  max 1.969 мс  ← НЕ ПОМОГАЕТ
SpinWait (жжём CPU)                 : p50 0.000  p95 0.001  max 0.433 мс
Гибрид Sleep(0)+SpinWait            : p50 0.000  p95 0.001  max 0.189 мс  ← выбор
```

`Thread.Sleep(1)` спит вдвое дольше запрошенного, а `timeBeginPeriod(1)` этого не чинит
(с Windows 10 2004 он влияет только на процесс и не возвращает старое глобальное поведение).
Значит **генератор пакетов должен работать на гибридном spin-wait в выделенном потоке** —
и это осознанно жжёт ядро CPU на время теста.

### 🟢 R-02 — Npcap: БЛОКЕР СНЯТ ОБХОДНЫМ ПУТЁМ

**Лицензионная картина (🔴 требует юридической проверки):**

- Бесплатная лицензия Npcap — **только 5 установок**, распространение **запрещено**,
  silent-инсталлятора нет (он только в OEM-версии).
- **Npcap OEM Redistribution** — платная. Цены публично не раскрыты: четыре тарифа
  по размеру компании, разовый выкуп + опциональная годовая поддержка, обращение в sales.
- **SharpPcap и PacketDotNet — LGPL-3.0.** Для закрытого продукта это означает: только
  динамическая линковка отдельными сборками, **запрет на ILMerge/статическую линковку**,
  публикация уведомления и возможность подмены DLL пользователем. Это **конфликтует
  с single-file/trimmed publish** — придётся исключать эти сборки из упаковки.

**Но главное — L2-инвентаризация оказалась возможна вообще без Npcap:**

```
A. SendARP (IPHLPAPI) — резолв IP→MAC БЕЗ Npcap и БЕЗ admin
   Шлюз 192.168.200.1 → MAC 00:00:5E:00:01:C8  (2.262 мс)  ✔ РАБОТАЕТ

B. GetIpNetTable — ARP-кэш ОС целиком: 332 записи

C. ИНВЕНТАРИЗАЦИЯ /24 БЕЗ ДРАЙВЕРА
   Живых узлов: 45 (ping-sweep 0.217 с)
   MAC получен для: 45 из 45 (SendARP 1.331 с)
   ИТОГО: 1.548 с, БЕЗ драйвера и БЕЗ admin
```

45 из 45 — стопроцентное покрытие. Плюс OUI → вендор, то есть тип устройства
угадывается уже на этом уровне.

**Что реально остаётся за Npcap:**

| Функция | Есть ли обход |
|---------|---------------|
| Приём LLDP/CDP-кадров | ✅ Да — через SNMP LLDP-MIB (см. R-05) |
| Пассивный анализ трафика | ❌ Нет |
| Детект rogue DHCP по broadcast | ⚠️ Частично — активным DHCP-запросом |
| Пассивный OS-fingerprint | ❌ Нет |
| Инжекция произвольных L2-кадров | ❌ Нет |

**Рекомендация: Npcap — опциональный плагин, а не зависимость ядра.**
Продукт полноценен без него. С ним получает пассивный анализ. Это снимает разом
лицензионный риск, риск UX первого запуска и риск конфликта LGPL с упаковкой.

Есть ещё **LLTD** (Link Layer Topology Discovery, `[MS-LLTD]`) — родной протокол Windows,
которым строится системная «Карта сети». Спецификация открыта. Работает только внутри
одной подсети (не маршрутизируется). Как дополнительный источник Evidence — интересен,
но нестандартен вне Windows-мира; в бэклог, не в v1.

### 🟡 R-03 — Агент: данные для решения собраны

Исследование не отвечает на вопрос протокола (это проектное решение Этапа 4), но
снимает два ограничения:

- Raw-сокеты доступны без admin → **агент может не требовать прав администратора**
  (кроме установки как службы).
- Шум UDP-стека 0.008 мс → точности хватит для честных throughput/jitter/PDV.

Открыто было: аутентификация, обнаружение агентов, прохождение firewall, обновление.
Спайк-05 закрыл первое и третье.

#### Спайк-05 (перед И-12): рукопожатие, темповка, firewall

**Рукопожатие — путь есть, и он единственный.**

| Проверка | Результат |
|----------|-----------|
| Самоподписанный сертификат в памяти, без хранилища и без прав | ✅ создаётся, ключ доступен |
| Первое сопряжение с пиннингом по отпечатку SHA-256 | ✅ 23.8 мс |
| Повторное подключение по запомненному отпечатку | ✅ 2.6 мс, подтверждения не требует |
| Подмена: тот же субъект `CN=storm-agent`, другой ключ | ✅ отвергнута |
| Проверка по цепочке доверия вместо пиннинга | ❌ отвергает и настоящий сертификат |

Последняя строка и есть вывод: у портативного агента нет ни центра сертификации,
ни прав на запись в хранилище, поэтому **доверие по цепочке для него невозможно
в принципе**, а пиннинг — не упрощение, а единственный доступный механизм. Подмена
при этом ловится: субъект и срок подделать нечего не стоит, отпечаток — нет.

Оговорка реализации: на Windows `SslStream` не принимает сертификат, собранный
`CertificateRequest.CreateSelfSigned`, напрямую — нужен круг через PFX
(`Export(Pfx)` → `LoadPkcs12`), иначе сервер не находит закрытый ключ.

**Темповка через настоящий сокет — лучше, чем ожидалось.**

Спайк-01 мерил таймер в пустом цикле. Здесь между тактами ещё и отправляется
датаграмма, то есть мерится связка «таймер + `SendTo`»:

```
интервал 1.0 мс, 2000 пакетов : p50 0.000  p95 0.000  p99 0.000  max 0.005 мс
интервал 0.5 мс, 2000 пакетов : p50 0.000  p95 0.000  p99 0.000  max 0.004 мс
интервал 0.1 мс, 5000 пакетов : p50 0.000  p95 0.000  p99 0.000  max 0.338 мс
```

10 000 пакетов/с выдерживаются с ошибкой такта ниже разрешения показа. Цена —
**101 % одного ядра из 16**: гибридный spin-wait занимает ядро целиком на время теста,
и это ровно то, о чём предупреждал спайк-01. Потолок отправки без темповки —
305 тыс. пакетов/с по 1400 байт (3.4 Гбит/с), то есть генератор не станет узким местом
раньше сети.

**Предусмотренный планом провал не наступил.** План закладывал «при провале — отказ
от UDP-теста в v1, throughput только по TCP». Отказываться не от чего.

**Firewall — вот где настоящее ограничение.**

| Проверка | Результат |
|----------|-----------|
| `bind` + `listen` на `0.0.0.0` без прав | ✅ успешно |
| Политика по умолчанию, все три профиля | `BlockInbound, AllowOutbound` |
| Добавить правило без прав администратора | ❌ «требуется повышение прав» |

Слушающий сокет открывается — и снаружи до него никто не достучится. Портативный
агент не может ни открыть себе порт, ни узнать, что он закрыт: с его стороны всё
выглядит исправно, а оператор видит таймаут. **Исходящие разрешены по умолчанию
во всех трёх профилях** — это и есть направление, в котором проходит соединение
без прав и без диалогов.

Отсюда вопрос, который решает не техника, а оператор: кто кому звонит.
Ответ зафиксирован в [плане](03-development-plan.md#и-12) и в [STATUS](STATUS.md).

### 🟢 R-04 — SNMP: библиотека найдена

**`Lextm.SharpSnmpLib`** — MIT, SNMP v1/v2c/v3, режимы manager и agent, async/await.
С v13 поддерживает только современный .NET (8/9/10), .NET Framework отброшен — для нас плюс.

**Проверено спайком-08 (И-17).** После Quartz брать библиотеку, читающую байты и считающую
хеши, без проверки под обрезкой нельзя. Проверялась вся цепочка на опубликованном бинарнике:

| Что проверяли | Итог |
|---------------|------|
| Вывод ключа из пароля: MD5, SHA-1, SHA-256, SHA-512 | 16 / 20 / 32 / 64 байта |
| AES: шифрование → расшифровка | совпало с исходным |
| Разбор BER на обеих сторонах: чтение и сборка ответа | работает |
| Обход таблиц `ifTable`, BRIDGE-MIB, LLDP-MIB | работает |
| Предупреждения обрезчика | нет |

Взято. Версия 12.5.7: у 13-й на момент И-17 только предвыпускные сборки.

**Отдельная находка, уже на публикации продукта.** Библиотека помечает свои методы
отправки атрибутом `RequiresUnreferencedCode` — то есть **сама объявляет себя
несовместимой с обрезкой**, и публикация продукта из-за этого не собирается вовсе
(IL2026 при `TreatWarningsAsErrors`). Спайк этого не показал: у него другой граф сборок.

Разрешено так же, как MSAGL в И-0, — внесением сборки в корни обрезки целиком: внутри
неё ничего не выкидывается, и то, о чём предупреждает атрибут, перестаёт быть возможным.
Цена измерена: **469 КБ** на консоль (22.86 → 23.33 МБ). После этого опубликованный
и обрезанный `storm.exe` читает у дублёра системную группу, порты, соседей и таблицу
пересылки — то есть проверено уже не на спайке, а на самом продукте.

Урок в копилку к спайку-08: **спайк проверяет библиотеку, но не проверяет продукт.**
Граф сборок у них разный, и предупреждение обрезчика, которого не было в спайке,
появилось на первой же публикации.

**Побочный урок спайка, стоящий записи.** С первого раза он провалился дважды — и оба
раза по моей вине, а не из-за обрезки: это выяснилось только потому, что тот же код
прогнали **без обрезки** и получили те же два отказа. Правило: у спайка на совместимость
обязан быть базовый прогон без неё, иначе «не работает после обрезки» и «не работает
вообще» неразличимы, а цена ошибки — отвергнутая зря библиотека.

Реальную долю отвечающего оборудования на этом стенде проверить по-прежнему нельзя
(нет управляемых свитчей). Вместо него в спайке живёт **коммутатор-дублёр**: отвечает
теми же байтами, что железо, растит счётчики, держит соседа по LLDP и таблицу пересылки.
Это испытательная оснастка, в поставку она не входит.

### 🟡 R-05 — LLDP/CDP: работает, но покрытие неполное

Через SNMP LLDP-MIB (`lldpRemTable`) — стандартный путь, Npcap не нужен. Ограничения,
подтверждённые источниками:

- LLDP не реализован в дешёвых и неуправляемых свитчах.
- **Неуправляемый свитч или хаб между инструментом и управляемым свитчем ломает топологию** —
  инструмент показывает неверную связность.
- ПК, принтеры, IoT-устройства себя не анонсируют — LLDP/CDP покрывает только сетевое
  оборудование и отдельные серверы.

**Это прямое подтверждение правильности модели Evidence из §2 анализа.** LLDP — источник
высокой достоверности там, где он есть; всё остальное достраивается эвристиками
с честно пониженной уверенностью. Показывать «уверенную» топологию там, где её нет, нельзя.

**Сделано в И-18.** Захват слушает LLDP и CDP своим адаптером и отвечает на вопрос,
который не берёт ни один другой источник: **в чей порт воткнуты мы сами**. SNMP на него
не ответит, пока нет учётных данных к коммутатору, а ARP и трассировка про порты
не знают вовсе.

Прослушивание идёт **без неразборчивого режима** — и это решение, а не недосмотр.
Соседство идёт на групповые адреса, которые карта принимает и так, ответы DHCP
широковещательны; неразборчивый режим добавил бы к этому чужой одноадресный трафик,
к диагностике отношения не имеющий. По той же причине в И-18 **не сделан пассивный
OS-fingerprint**, хотя он значился в плане: без неразборчивого режима он видел бы
только тех, кто разговаривает с нами, а включать этот режим ради него — плохой обмен.

### 🟢 R-14 — Хранилище: SQLite достаточно

SQLite тянет временные ряды при двух условиях: **downsampling и retention обязательны,
а не опциональны.** Схема: сырые сэмплы с горизонтом (например, 90 дней) + таблица

DuckDB (колоночный, в 10–50 раз быстрее на агрегатах) — **не в v1.** Появится, если
отчёты за год начнут тормозить.

### 🔴 R-15 — Планировщик: Quartz.NET **отвергнут при проверке**

Решение принималось до того, как публикация с обрезкой стала свойством продукта,
и не пережило встречи с ней. Перед И-14 сделан [`spike-06-scheduler`](../spikes/spike-06-scheduler):
Quartz 3.19 с persistent store на SQLite, ровно та конфигурация, которая требовалась
по C-05/C-06.

| Сборка | Что произошло |
|--------|---------------|
| без обрезки | доходит до запроса `QRTZ_JOB_DETAILS` — работает, ждёт свои 11 таблиц |
| **с обрезкой** | **падает на `GetScheduler()`**: `Cannot instantiate type which has no empty constructor (SimpleTypeLoadHelper)` |
| предупреждений при сборке | **ноль** |

Причина в устройстве библиотеки: типы создаются по имени (`Type.GetType`), провайдер
базы выбирается строкой `"SQLite-Microsoft"`, задание в хранилище — это сериализованное
имя CLR-типа. Обрезчик удаляет то, на что нет статических ссылок, и ни о чём
не предупреждает, потому что предупреждать не о чем: ссылок нет.

**Библиотека, ломающаяся молча на машине пользователя, хуже собственного кода.**
Ошибка при сборке была бы поводом настроить корни обрезки; отсутствие ошибки —
это ловушка, которая срабатывает после выпуска.

**Что сделано вместо.** Разобрано, что из Quartz нам действительно нужно, и оказалось —
одно: **срок, переживающий выключение машины**. Он лежит полем `next_due_ticks`
в нашей же базе, схема которой versioned и наша. Остальное Quartz даёт для сервера:
кластеризация, пулы потоков, слушатели, календари — ничего из этого в настольном
продукте не работает.

Написано своё: `CronExpression` (пять полей, ~250 строк, разбор строки в наборы чисел —
рефлексии не требует и обрезкой сломан быть не может по устройству), `Schedule`
с misfire-политикой и окнами обслуживания, `MonitorScheduler` поверх `TimeProvider`.
Покрыто 42 тестами расписания и 22 тестами cron, включая DST и «30 февраля».

**Обратимость.** Планировщик отделён от мониторов портом `IMonitorStore` и службой
`MonitorService`: если решение придётся пересмотреть, меняется один класс, а не итерация.

Hangfire и Coravel не рассматривались заново — они отпали по другим причинам
(дашборд-ориентированность и отсутствие persistence) и от обрезки не легче.

### 🟢 R-19 — Упаковка: замерено

| Режим публикации | Размер |
|------------------|--------|
| Framework-dependent | **0.2 МБ** (нужен установленный .NET) |
| Self-contained, single-file, trimmed | **11.7 МБ** |
| NativeAOT | ❌ **не собрался**: `Platform linker not found` — требует workload «Desktop development with C++» в Visual Studio |

NativeAOT добавляет зависимость сборочной среды от C++ toolchain и плохо уживается
с рефлексией. Для v1 не нужен — **берём self-contained single-file**.

11.7 МБ для полностью автономного приложения — отлично (для сравнения, Electron-приложение
начинается со ~150 МБ). **Оговорка:** trimming несовместим с LGPL-сборками SharpPcap —
ещё один аргумент выносить Npcap-функционал в отдельный опциональный плагин.

**Velopack** — преемник Squirrel: дельта-обновления, кроссплатформенность, сборка одной
командой. Был рекомендацией, стал решением — но только после проверки.

**Проверено спайком-07 (И-16).** После истории с Quartz (R-15) рекомендовать библиотеку,
читающую JSON, без проверки под обрезкой нельзя. Проверялась вся цепочка на опубликованном
бинарнике — self-contained, single-file, trimmed:

| Что проверяли | Итог |
|---------------|------|
| Разбор ленты `releases.win.json` | 3 записи, версии и типы прочитаны верно |
| Определение установки, текущая версия | `IsInstalled = true`, `1.0.0` |
| Поиск обновления | найдено `1.0.1` |
| Скачивание, контрольная сумма, разностный пакет | собран, `2.7 КБ` против `9.9 МБ` полного |
| Предупреждения обрезчика | нет |

Применение обновления делает `Update.exe` — он на Rust, к обрезке отношения не имеет.

**Velopack принят.** Это первый случай, когда внешняя библиотека прошла проверку
на обрезку, и он же показывает, что правило «не доверяй, а измерь» работает в обе
стороны: Quartz отвергнут по измерению, Velopack принят по нему же. Inno Setup как
запасной вариант больше не нужен.

**Авто-обновление при этом не молчаливое.** Продукт измеряет; подменить свою версию
посреди суточного мониторинга значит разорвать ряд измерений надвое и не сказать об этом.
Условия измерения хранятся вместе с каждым прогоном именно затем, чтобы такие разрывы
были видны, — устраивать их самому было бы прямым противоречием. Поэтому проверка идёт
сама, установка — по команде оператора и никогда во время работающего прогона.

### 🟢 R-21 — Раскладка графа: готовые компоненты проходят, но не любые

**Спайк-04** ([spikes/spike-04-graph](../spikes/spike-04-graph)), выполнен перед И-9,
как требует план. Проверялся движок MSAGL (`AutomaticGraphLayout` 1.1.12) — тот самый,
что `AvaloniaGraphControl` несёт внутри себя. Обе библиотеки под MIT, к нашей лицензии
претензий нет.

Граф брался формы настоящей сети: несколько маршрутизаторов, десяток коммутаторов,
остальное — конечные узлы. Случайный граф той же плотности раскладывается иначе,
и мерить на нём значило бы мерить не то.

| Узлов | Ярусная (Sugiyama) | Полотно | По расстояниям (MDS) | Полотно |
|-------|--------------------|---------|----------------------|---------|
| 36    | 32 мс              | 15.6 : 1 | 16 мс               | 1.3 : 1 |
| 91    | 135 мс             | 27.3 : 1 | 63 мс               | 1.3 : 1 |
| **300** | **280 мс**       | **64.8 : 1** | **361 мс**      | **1.7 : 1** |
| 609   | 426 мс             | 108 : 1  | 1073 мс             | 1.3 : 1 |
| 1026  | 739 мс             | 158 : 1  | 2610 мс             | 1.5 : 1 |

**По времени порог пройден с запасом**: 300 узлов раскладываются за треть секунды при
бюджете в секунду, память — 26 МБ. Собственный рендер поверх Skia не нужен, объём И-9
остаётся плановым.

**Но спайк нашёл второй порог, которого в плане не было — вытянутость полотна.**
Ярусная раскладка для сети из 300 узлов даёт полотно 32517 × 502 точки, то есть
**65 : 1**. Формально это успех: быстро и корректно. На деле — не карта, а список,
выложенный в строку, по которому нужно скроллить горизонтально минуту. Причина в форме
данных: у сети мало уровней и очень много листьев, а ярусная раскладка кладёт каждый
уровень в ряд.

**Три следствия для И-9:**

1. **Раскладка по расстояниям, а не ярусная.** MDS держит соотношение сторон около
   1.5 : 1 на всех размерах. Ярусная останется — но для другого вопроса: путь
   трассировки это направленная цепочка, и там она как раз уместна.
2. **Потолок MDS — примерно 500 узлов на секунду.** Дальше время растёт быстрее
   линейного: 609 узлов — 1.1 с, 1026 — 2.6 с.
3. **Конечные узлы сворачиваются в счётчик на коммутаторе.** Свёрнутая форма
   (только структура) раскладывается за 5–36 мс, и триста отдельных прямоугольников
   с адресами всё равно не карта. Разворачивать — по требованию.

## 3. НОВОЕ: риски, которых не было в анализе

### 3.1 🔴 Виртуальные адаптеры и VPN искажают измерения

Обнаружено эмпирически. На стенде (Hyper-V vSwitch):

```
Обычный приоритет : p50 0.496  p95 0.881  p99 8.915  max 10.362 мс
High + timeBeginPeriod: p50 0.474  p95 0.786  p99 11.303  max 11.540 мс
```

p99 в **18 раз** выше p50. Повышение приоритета процесса и потока **не помогло** —
стало даже хуже. Источник выбросов не наш код и не GC (0 пауз), а виртуальный коммутатор.

**Следствие — новое требование:** продукт обязан определять тип адаптера (физический /
виртуальный / VPN / Wi-Fi) и **предупреждать оператора**, что измерения через vSwitch или VPN
содержат собственный шум. Иначе пользователь припишет джиттер гипервизора своей сети.
Это же — повод добавить в отчёт секцию «условия измерения».

### 3.2 🔴 QuestPDF не подходит части заказчиков

Публичные компании и госсектор не подпадают под Community-лицензию **независимо от выручки**.
Если целевой рынок включает госзаказчиков — либо платная лицензия сразу, либо PDFsharp.
Отсюда требование изолировать генератор отчётов за интерфейсом.

### 3.3 ~~🟡 LGPL SharpPcap конфликтует с упаковкой~~ — снято в И-18

**Предпосылка была неверна.** SharpPcap 6.3.1 распространяется по **MIT**, а не LGPL-3.0:
это записано в `<license type="expression">MIT</license>` его собственного nuspec.
Библиотека сменила лицензию, а риск, записанный на этапе исследования, вместе с ней
исчез. Требования к возможности подмены нет, конфликта с обрезкой и упаковкой в один
файл — тоже.

Спайк-09 снял и остальные основания для динамической загрузки:

- типы `SharpPcap` поднимаются **без установленного драйвера** — держать библиотеку
  в основном бинаре безопасно, экран возможностей не упадёт у того, у кого Npcap нет;
- обрезку библиотека переживает — выносить её из бандла незачем;
- отказ конкретен и опознаваем: `DllNotFoundException`, а `Pcap.Version` вообще
  отвечает строкой, ничего не роняя.

**Решение И-18:** `plugins/` остаётся единственным местом со ссылкой на SharpPcap —
это проверяется архитектурным тестом, — но подключается плагин обычной ссылкой.
`AssemblyLoadContext` поверх однофайлового обрезанного хоста добавил бы целый класс
отказов ради нуля выгоды.

**Что осталось в силе полностью:** Npcap не входит в поставку ни при каких условиях.
Это ограничение NPSL, а не SharpPcap, и оно никуда не делось.

Урок в копилку к спайкам 06–08: **лицензия — тоже допущение, и она тоже устаревает.**
Проверять её надо у пакета, который берёшь сегодня, а не у того, о котором читал год назад.

### 3.4 🟡 Период низкой репутации у SmartScreen неизбежен

EV больше не решает проблему. Первые сотни пользователей увидят предупреждение
независимо от того, сколько мы заплатим за сертификат.

## 3.5 ДОПОЛНЕНИЕ: продукт открытый — что это меняет

Решение оператора об open-source (принято после первой сдачи отчёта) потребовало
доисследования трёх пунктов.

| Пункт | Было | Стало |
|-------|------|-------|
| **QuestPDF** | 🔴 Риск: не для публичных компаний и госсектора | 🟢 **Снят.** Community-лицензия прямо покрывает open-source проекты |
| **Подпись кода** | 🔴 OV ~$225/год + период низкой репутации | 🟢 **SignPath Foundation — бесплатная OV-подпись для OSS.** Условия: OSI-одобренная лицензия, публичный репозиторий, воспроизводимая сборка из него, активная поддержка. ⚠️ Издателем в SmartScreen будет значиться «SignPath Foundation», а не мы |
| **SharpPcap** | 🟡 Считался LGPL-3.0: ограничения на линковку и упаковку | 🟢 **С версии 6 — MIT** (проверено по nuspec в И-18). Ограничений не осталось; обрезку переживает, см. спайк-09 |
| **Npcap** | Предполагалось: OEM-лицензия за деньги | 🔴 **Хуже, чем думали.** NPSL основана на GPLv2, но **не является open-source** и запрещает распространение без отдельного разрешения. У Wireshark для этого именное исключение; для других OSS-проектов разрешение запрашивается индивидуально |

**Ключевой вывод по Npcap:** открытость нашего кода **не даёт** права его распространять.
Значит подтверждается решение §2 `R-02`: **Npcap не входит в дистрибутив ни в каком виде.**
Продукт детектирует уже установленный драйвер; установку выполняет пользователь сам
с официального сайта. Это одновременно и правовое, и UX-решение.

**Новое требование, вытекающее из условий SignPath:** сборка релиза должна быть
воспроизводима из публичного репозитория. Это влияет на CI и на процесс релиза —
учесть в плане Этапа 4.

**Новое решение к принятию:** конкретная лицензия проекта. Должна быть OSI-одобренной
(условие SignPath). Рекомендация — **MIT**; принята в И-0. Оговорка про совместимость
с LGPL-плагином захвата снята в И-18 вместе с самой предпосылкой: SharpPcap оказался MIT.

Источники: [Nmap/Npcap Legal Notices](https://nmap.org/book/man-legal.html) ·
[SignPath Foundation — условия для OSS](https://signpath.org/terms.html) ·
[SignPath для open source](https://signpath.io/solutions/open-source-community)
