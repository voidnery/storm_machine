## ДОПОЛНЕНИЕ ПО ИТОГАМ ЭТАПА 2 (2026-08-25): выбран **Avalonia**

Развилка Avalonia vs WPF закрыта фактами, а не предпочтениями:

| Аргумент | Вес | Итог |
|----------|-----|------|
| **`R-13` — редактор графа топологии** (самый дорогой UI-компонент) | Решающий | Под Avalonia экосистема node-editor богаче: Nodify.Avalonia, NodeEditorAvalonia, NodifyM.Avalonia и **AvaloniaGraphControl с авто-раскладкой MSAGL**. Под WPF выбор беднее |
| `R-12` — графики | Нейтральный | ScottPlot и LiveCharts2 поддерживают обе платформы |
| `R-11` — PDF | Нейтральный | QuestPDF не зависит от GUI |
| `R-20` — путь к web-панели | В пользу Avalonia | Кроссплатформенное ядро + возможность общего кода при переходе |
| `R-01`, `R-10` — доступ к Windows API и точность | Нейтральный | P/Invoke и `Stopwatch` одинаковы; замеры проводились на консольном .NET и от GUI не зависят |
| Зрелость и тулинг | В пользу WPF | Единственный весомый довод против. Принимается как осознанная цена |

**Подтверждено эмпирически (Этап 2):** .NET проходит требование §6 по точности —
собственный джиттер измерительного стека **0.008 мс**, GC-пауз за 300 замеров **0**.
Опасение `[R-10]`, которое могло отвергнуть весь стек, снято.

## УТОЧНЕНИЕ ВЕРСИЙ (2026-08-25, при старте И-0)

При создании проектов выяснились два обстоятельства, меняющие версии — но не сам выбор.

**1. Рантайм: .NET 10, а не .NET 8.**
LTS-поддержка .NET 8 заканчивается **в ноябре 2026** — через три месяца. Стартовать
на нём новый продукт означало бы мигрировать сразу после первого релиза. .NET 10 — текущая
LTS с поддержкой до ноября 2028. На машине разработки установлены оба SDK (8.0.301
и 10.0.201) и оба рантайма, так что переход бесплатен.

Spike-программы 01–03 остаются на net8.0 — это исследовательские артефакты, переписывать
их незачем. Проверку точности на .NET 10 закрывают автотесты итерации И-1: если рантайм
поведёт себя хуже, тест «шум стека ≤ 20%» это поймает.

**2. GUI: Avalonia 12, а не 11.**
Актуальная стабильная версия — 12.1.1. Ключевой вопрос был в том, поспела ли за ней
экосистема редакторов графа, ради которой Avalonia и выбиралась (`R-13`). Проверено
по NuGet:

| Библиотека | Версия | Требует |
|-----------|--------|---------|
| Nodify.Avalonia | 2.0.0 | Avalonia ≥ 12.0.5 |
| NodifyM.Avalonia | 12.0.0 | Avalonia ≥ 12.0.2 |
| NodeEditorAvalonia | 12.0.0 | Avalonia ≥ 12.0.0 |
| AvaloniaGraphControl | 0.8.0 | Avalonia ≥ 12.0.1 |

Все четыре кандидата уже на Avalonia 12 — вывод `R-13` в силе, риск не возник.

## Контекст

Нужно выбрать платформу для настольного GUI-приложения под Windows, которое одновременно:

1. **Лезет глубоко в сетевой стек ОС** — ICMP с контролем TTL и DF, raw/UDP-сокеты,
   таблицы ARP и маршрутизации, IP Helper API, при возможности L2-захват, WLAN API, SNMP.
2. **Измеряет время с миллисекундной достоверностью.** Паузы сборщика мусора, GIL или
   планировщика рантайма напрямую подмешиваются в измеряемый джиттер. Это не «оптимизация» —
   это вопрос валидности продукта. Требование §6: собственный джиттер стека ≤ 20% измеряемой величины.
3. **Рисует нагруженный UI** — живые графики с обновлением ~10 Гц, интерактивный редактор
   графа топологии, таблицы на тысячи строк.
4. **Генерирует PDF** приличного полиграфического качества.
5. **Готовится к переезду** на архитектуру «сервер + web-панель» без переписывания ядра.
6. **Упаковывается в один инсталлятор**, подписывается, и не выглядит подозрительно для EDR.

Требование №6 из списка выше (переиспользование ядра в будущем сервере) — **самый сильный
дифференциатор** между вариантами: он требует, чтобы язык ядра одинаково хорошо жил
и в десктопе, и в серверном рантайме.

Доступное на машине разработки (проверено): Python 3.11.5, .NET SDK 8.0.301 и 10.0.201,
Node 22.12.0, Go 1.26.7.

## Рассматриваемые варианты

### Вариант A: C# / .NET + Avalonia (или WPF)

Ядро — библиотека .NET; GUI — Avalonia (кроссплатформенно, пригодится позже) или WPF (нативнее под Windows).
Будущий сервер — ASP.NET Core, переиспользующий **тот же** проект ядра.

| Измерение | Оценка |
|-----------|--------|
| Сложность | Средняя |
| Доступ к Windows API | **Отличный** — P/Invoke к IPHLPAPI, WlanAPI, прямая работа с сокетами |
| Точность таймингов | Хорошая — но нужна проверка влияния GC `[R-10]` |
| Экосистема (PDF, графики, SNMP, граф) | Богатая — но лицензии проверить `[R-11]`, `[R-12]`, `[R-13]` |
| Путь к server+web | **Отличный** — ядро переезжает без изменений |
| Упаковка | Отличная — single-file publish, MSI/MSIX, подпись |
| Знакомство команды | ? — вопрос к оператору |

**За:** лучший баланс «системный доступ + производительность + скорость разработки»; единый язык для
десктопа, будущего сервера и агента; зрелые async-примитивы для тысяч параллельных проб.
**Против:** GC-паузы требуют проверки; выбор GUI-фреймворка — отдельное решение; при выборе WPF
кроссплатформенность будущего сервера ограничивается фронтендом (ядро — нет).

---

### Вариант B: Python 3.11 + PySide6/Qt

| Измерение | Оценка |
|-----------|--------|
| Сложность | **Низкая** — самая быстрая разработка |
| Доступ к Windows API | Хороший — ctypes, scapy, pysnmp |
| Точность таймингов | **Слабое место** — GIL и интерпретатор в горячем пути измерений `[R-10]` |
| Экосистема | Богатейшая для сети; UI-графики и PDF слабее |
| Путь к server+web | Хороший — FastAPI переиспользует ядро |
| Упаковка | **Слабое место** — PyInstaller: большой размер, медленный старт, частые ложные срабатывания антивирусов `[R-16]`, `[R-19]` |
| Знакомство команды | ? |

**За:** максимальная скорость прототипирования; scapy закрывает почти весь L2/L3-функционал.
**Против:** два серьёзных риска сразу — точность измерений и упаковка/антивирусы. Для продукта,
чья ценность в точности цифр, первый риск концептуальный. Митигируется вынесением измерительного
ядра в нативный модуль — но это фактически гибрид, а не чистый вариант B.

---

### Вариант C: Go + Wails / Fyne

| Измерение | Оценка |
|-----------|--------|
| Сложность | Средняя |
| Доступ к Windows API | Хороший — syscall, gopacket |
| Точность таймингов | **Отличная** — низкие GC-паузы, дешёвая конкурентность (десятки тысяч проб) |
| Экосистема | Сеть — отличная; **UI, графики, PDF — слабое место** `[R-11]`, `[R-12]`, `[R-13]` |
| Путь к server+web | **Отличный** — Go рождён для этого |
| Упаковка | **Отличная** — один статический бинарь |
| Знакомство команды | ? |

**За:** лучший рантайм для измерений и для будущего сервера; идеален для `storm-agent`.
**Против:** десктопный GUI — самая слабая часть экосистемы. Редактор графа топологии и живые
графики придётся либо писать самим, либо тащить веб-вью (что превращает вариант в D).

---

### Вариант D: Web-стек в оболочке — Tauri (Rust) или Electron (Node)

| Измерение | Оценка |
|-----------|--------|
| Сложность | Средняя (Electron) / **Высокая** (Tauri+Rust) |
| Доступ к Windows API | Node — ограниченный; Rust — отличный |
| Точность таймингов | Node — слабая; Rust — отличная |
| Экосистема UI | **Лучшая из всех** — графы, графики, таблицы, live-обновление |
| Путь к server+web | **Лучший из всех** — фронтенд переиспользуется в web-панели напрямую |
| Упаковка | Electron — тяжёлая (~150 МБ); Tauri — лёгкая |
| Знакомство команды | ? |

**За:** UI-часть (топология, графики) решается на порядок дешевле; будущая web-панель —
буквально тот же фронтенд.
**Против:** Electron не тянет требование точности; Tauri требует Rust — самый долгий путь
к первому работающему результату.

---

### Вариант E: Гибрид — нативное ядро + web-UI

Ядро измерений и API на .NET или Go; UI — веб-фронтенд в локальной оболочке; связь по локальному HTTP/WebSocket.

**За:** каждый слой на своей сильной стороне; переход к server+web — уже почти сделан
(ядро становится сервером, фронтенд — панелью, меняется только адрес API).
**Против:** две технологии и два процесса с первого дня; сложнее отладка, сборка и установка;
выше начальная стоимость.

## Предварительная сводная оценка

Веса отражают приоритеты §6 анализа. Оценки предварительные — уточняются на Этапе 2.

| Критерий | Вес | A (.NET) | B (Python) | C (Go) | D (Tauri) | E (Гибрид) |
|----------|-----|----------|-----------|--------|-----------|------------|
| Точность измерений | ×3 | 4 | 2 | 5 | 5 | 5 |
| Доступ к Windows API | ×3 | 5 | 4 | 4 | 4 | 5 |
| Богатство UI (граф, графики) | ×3 | 3 | 3 | 2 | 5 | 5 |
| Качество PDF-отчётов | ×2 | 4 | 3 | 2 | 4 | 4 |
| Путь к server+web | ×2 | 5 | 4 | 5 | 5 | 5 |
| Скорость разработки | ×2 | 4 | 5 | 3 | 2 | 2 |
| Упаковка и антивирусы | ×2 | 5 | 2 | 5 | 4 | 3 |
| **Взвешенно (макс. 85)** | | **66** | **50** | **56** | **68** | **69** |

Разрыв между A, D и E — в пределах погрешности предварительных оценок. Именно поэтому
решение откладывается: разницу должны решить **факты** `[R-10]` (реальная точность таймингов
на прототипе), `[R-13]` (стоимость редактора графа) и `[R-11]` (качество PDF), а не догадки.

## Что решит вопрос (эксперименты Этапа 2)

1. **Spike точности.** На двух-трёх кандидатах: 10 000 ICMP-echo к локальному узлу,
   сравнение с эталоном (аппаратный/`hping3`/выделенная утилита). Метрика — собственный джиттер стека.
2. **Spike графа.** Прототип редактора топологии на 300 узлах: раскладка, перетаскивание,
   выделение, производительность.
3. **Spike PDF.** Один и тот же отчёт (титул, таблицы, 4 графика, схема) на кандидатах — сравнение вёрстки.
4. **Spike упаковки.** Сборка «hello world» каждого кандидата → прогон через VirusTotal и
   типовой корпоративный EDR `[R-16]`.
5. **Юридическая проверка** лицензий всех кандидатных библиотек `[R-02]`, `[R-08]`, `[R-09]`, `[R-11]`.

## Последствия (для любого выбранного варианта)

Независимо от исхода, эти правила фиксируются **сейчас**:

- Ядро (домен + приложение + пробы) — отдельный модуль, **не знающий о UI**. Нарушение = блокер ревью.
- Контракт между UI и ядром описан явно и сериализуем — чтобы завтра стать сетевым API.
- Измерительный горячий путь изолирован и заменяем: если рантайм не даст точности,
  меняем только его, а не приложение.
- `storm-agent` — отдельный артефакт с собственным жизненным циклом; допускается на другой технологии.
