## 1. Слои и направление зависимостей

```
   Presentation          App (Avalonia)        Cli            Agent
                                │                │               │
                                └────────┬───────┘               │
                                         ▼                       │
   Composition              StormMachine.Composition ◄───────────┘
                                    │         │
                                    ▼         ▼
   Application         StormMachine.Application │
                                    │          │
                                    ▼          │
   Domain               StormMachine.Domain    │
                                    ▲          │
                                    │          ▼
   Infrastructure     Probes · Platform · Discovery · Storage
                      Reporting · Scheduling · Protocol
                                         ▲
                                         │
   Plugins                  Capture.Npcap (опционально)
```

**Правило:** зависимости направлены внутрь. `Domain` не знает никого. Инфраструктура
реализует интерфейсы, объявленные в `Application`, и подключается через DI.

**`Composition` — единственное исключение.** Это корень композиции: ему разрешено знать
обо всех слоях сразу, потому что кто-то должен связать порты с реализациями. Появился
в И-1, когда выяснилось, что иначе CLI пришлось бы ссылаться на инфраструктуру напрямую
и правило 3 пришлось бы ослабить. Выгода на будущее: серверный вариант соберёт продукт
тем же вызовом `AddStormMachine()`.

## 3. Правила, проверяемые тестами

`tests/StormMachine.ArchTests` содержит правила, нарушение которых **роняет сборку**:

| № | Правило | Зачем |
|---|---------|-------|
| 1 | `Domain` не ссылается ни на один проект и ни на один NuGet-пакет | Чистота модели |
| 2 | `Application` ссылается только на `Domain`; из пакетов — лишь `*.Abstractions` | Инверсия зависимостей |
| 3 | `App` и `Cli` не ссылаются на инфраструктуру напрямую | Ядро не прирастает к интерфейсу |
| 4 | SharpPcap и PacketDotNet — только в `plugins/` | Изоляция LGPL + работоспособность trimming |
| 5 | Avalonia — только в `StormMachine.App` | Ядро не знает о существовании UI |
| 6 | `PingReply.RoundtripTime` не встречается в коде `src/` (комментарии не в счёт) | Принцип 8.2.8: API даёт целые миллисекунды |
| 7 | Типы QuestPDF не выходят за пределы `Reporting` | Заменяемость PDF-движка |

Отдельно от тестов, но в том же ряду: **CI собирает клиенты публикацией с обрезкой
на каждое изменение**. Правило появилось после И-9, где выяснилось, что публикация была
сломана с И-3 и семь итераций этого никто не видел — тесты проходили, а обрезчик
запускался только по тегу релиза.

Правило 6 проверяется по коду с вырезанными комментариями — упоминание запрещённого API
в пояснении, почему он запрещён, нарушением не является. Само вырезание покрыто
отдельными тестами (`CommentStrippingTests`): иначе правило могло бы незаметно
перестать что-либо ловить, продолжая гореть зелёным.

## 4. Ключевые абстракции

### `IProbe` — проба как плагин

Единый интерфейс для всех измерений. Объявляет свои параметры декларативно —
UI строит форму по декларации, поэтому новая проба **не требует правки интерфейса**.

Контракт: описание параметров → валидация → выполнение с отменой → поток сэмплов →
агрегация → вердикт.

### `Result` — два канала: сэмплы и факты

Каждая проба отдаёт **поток сырых сэмплов** (для живого графика) и **агрегацию**
(для истории и отчёта). Общая часть хранится в колонках, специфика пробы — в JSON-поле.

Рядом с числовым каналом идёт второй — **факты** (`ProbeFact`): записи DNS, цепочка
сертификатов, код ответа и заголовки HTTP. Разделение введено в И-2, когда выяснилось,
что половина проб сообщает не только «сколько миллисекунд», но и «что именно там
оказалось», и это не укладывается в числовой ряд.

Разделение защищает горячий путь: `Sample` остаётся лёгкой структурой, а словарь фактов
не появляется у каждого из десятков тысяч сэмплов ICMP-серии.

Факты доходят до результата через `IProbeObserver` — побочный канал, который вызывающая
сторона передаёт в пробу. Пробы зарегистрированы как singleton, поэтому состояние
конкретного прогона не может жить на самой пробе.

### Графический клиент: где проходит граница

`StormMachine.App` ссылается только на `Application` и `Composition` — как и консоль.
Ядро собирается тем же вызовом `AddStormMachine()`.

**Типы ScottPlot не выходят за пределы слоя представления.** Модель представления отдаёт
числа и сообщает, что они изменились; чем именно их нарисовать — дело кода за разметкой.
Принцип 10 (внешние библиотеки за собственными интерфейсами) здесь соблюдается
разделением файлов, а не введением ещё одной абстракции: рисование графика и есть
задача представления.

**График обновляется по таймеру на 10 Гц, а не на каждый сэмпл.** Монитор с интервалом
100 мс дал бы десять обращений к диспетчеру в секунду на каждый прогон; при нескольких
прогонах это заметное дёрганье без всякой пользы — человек не различает больше десятка
обновлений в секунду. Сэмплы копятся в очереди, страница разбирает её по тику.

**`ViewLocator` сопоставляет модель и представление явно, а не по соглашению об именах.**
Поиск типа по строке при обрезке молча перестал бы находить представления — у пользователя,
а не при сборке. Правило 8 архитектурных тестов проверяет, что ни одна страница
не осталась без представления.

**`RunnerService`** держит выполняющиеся прогоны для Run Drawer. Прогон не останавливается
при уходе со страницы: он виден в панели и продолжает писаться в журнал. Останавливать
измерение потому, что оператор переключил вкладку, — потеря данных без причины.

### Отчёт: почему он появился рано

Отчёт сделан в И-6, а не в конце, намеренно: **его форма определяет, какие метаданные
обязано сохранять измерение**. Отложи мы его к завершению — обнаружили бы нехватку
данных, когда исправлять дорого.

Документ отвечает на два вопроса, без которых цифры бесполезны: **по какой методике**
измеряли и **в каких условиях**. Отчёт со ссылкой на RFC — аргумент в разговоре
с провайдером; отчёт без методики — просто картинка.

`IReportRenderer` существует не ради абстракции как таковой, а ради конкретного риска
(`R-11`): выбранный движок PDF бесплатен при определённых условиях, и они могут перестать
выполняться. За этой границей замена стоит день. Архитектурное правило 7 проверяет,
что типы QuestPDF не выходят за пределы `Reporting`.

**График для отчёта светлый, а не тёмный как в приложении.** Это не оплошность: отчёт
печатают и пересылают, а тёмная заливка на бумаге превращается в чёрный прямоугольник.
Поэтому общего кода с живым графиком у него нет — это разные задачи, а не дубль.
`Reporting` использует ядро ScottPlot **без Avalonia**: рисование в изображение
не требует графической подсистемы, и правило «Avalonia только в клиенте» не нарушается.

### Пресеты: версия без истории версий

Пресет хранит версию, но **история редакций не хранится**. Причина в том, что прогон
уже самодостаточен: он сохраняет фактические параметры, с которыми выполнялся, и потому
истолковывается без обращения к пресету. Версия нужна лишь чтобы было видно — результат
получен пресетом второй редакции, а в библиотеке сейчас пятая, и сравнивать их напрямую
нельзя.

Версия растёт **только при изменении того, что влияет на измерение**: пробы, цели или
параметров. Переименование и правка описания её не трогают — иначе счётчик версий
перестал бы что-либо значить.

Проверка пресета опирается на объявление пробы — тот же источник, из которого строятся
формы в интерфейсе и ключи командной строки. Третье применение одного объявления:
добавляя пробу, мы бесплатно получаем и проверку её пресетов.

### Кодировка в JSON-полях

Сериализация в базе и в файлах обмена использует кодировщик, не экранирующий кириллицу.
Это не косметика: с экранированием по умолчанию тег «сеть» уезжает в базу как
`сеть`, и поиск подстроки перестаёт находить то, что ввёл человек.

Поиск по имени, описанию и тегам делается **в памяти, а не в SQL**: функция `LOWER()`
в SQLite приводит к нижнему регистру только латиницу, и «Шлюз» никогда не совпал бы
с «шлюз».

### Хранилище: что в колонках, что в JSON

Разделение проведено по одному признаку — **по чему ищут и сортируют**. Имя пробы, цель,
время, число проб, потери, медиана лежат в колонках. Условия измерения, факты и параметры
пробы — в JSON. Попытка разложить специфику четырёх форм результата по колонкам дала бы
таблицу из почти всегда пустых полей.

**Ключ таблицы сэмплов — `(прогон, порядок поступления)`, а не `(прогон, номер)`.**
У фазовых проб порядковый номер повторяется: пять фаз одного запроса HTTP несут один
номер попытки. Порядок поступления — единственное, что уникально во всех четырёх формах.

**Агрегаты считаются при записи, а не при чтении.** Политика хранения удаляет сырые сэмплы,
а `run_series` остаётся: история и отчёты за год продолжают работать, когда подробностей
уже нет. Пересчитать их потом было бы не из чего.

Три состояния прогона различаются намеренно: **завершён**, **прерван оператором**
и **оборван сбоем**. Последнее выставляется при следующем открытии базы для записей,
оставшихся открытыми. Такой прогон не удаляется — сэмплы, записанные до сбоя, остаются,
а агрегаты для него считаются на лету при чтении.

### `ProbeResultShape` — форма результата

Шесть проб дали **четыре несводимые формы данных**:

| Форма | Пробы | Что это |
|-------|-------|---------|
| `ScalarSeries` | ICMP, TCP, UDP | Один ряд чисел во времени |
| `PhasedTiming` | HTTP, TLS | Одно событие, разложенное на фазы |
| `ComparedSeries` | DNS | Несколько рядов для сравнения между собой |
| `PathTrace` | Traceroute | Матрица «хоп × попытка» |

Проба **объявляет** форму, а не даёт угадать по содержимому сэмплов. Угадывание работало бы
до первой пробы, не вписавшейся в эвристику. По объявлению строится и показ, и (начиная
с И-3) схема хранения.

Ради двух последних форм в `Sample` добавлены `Label` (фаза, резолвер, узел) и `Group`
(хоп, попытка). Для скалярных проб оба поля остаются пустыми.

### `PathAnalysis` — правило чтения трассировки

Появился в И-7. Разбирает матрицу «хоп × попытка» в таблицу хопов, список смен маршрута
и **точку деградации**. Последнее — единственное здесь, что нельзя было отдать показу:
это правило, а не оформление.

Самая частая ошибка чтения traceroute — принять потери на промежуточном хопе за поломку
канала. Транзитный узел ограничивает частоту собственных ответов на ICMP, но исправно
передаёт трафик. Отсюда три следствия, закреплённые тестами:

1. Точка деградации ищется **от конца назад** и объявляется только если потери дошли
   до конечного узла. Молчащие хопы по пути пропускаются: узел, не отвечающий вовсе,
   ничего не сообщает о судьбе транзита.
2. `VoiceQuality` на транзитных хопах считается по задержке и дрожанию, **без потерь**.
   На конечном узле потери учитываются полностью — там они настоящие.
3. Молчащие хопы объясняются отдельной строкой, а не показываются как стопроцентные
   потери без пояснения.

**Конечная точка — последний хоп, ответивший целью.** Цель регулярно отвечает
с нескольких TTL сразу: в туннеле MPLS без переноса TTL весь туннель считается одним
хопом, и при смене маршрута внутри него цель оказывается то ближе, то дальше. Считать
конечной точкой первое совпадение значило бы объявить «до цели 97% потерь» там, где
потерь нет. Ранние совпадения перечисляются в `EarlyDestinationHops` и объясняются
показу отдельной строкой.

`PathAnalysis.Compute` работает по сырым сэмплам, `PathAnalysis.FromSeries` — по
сохранённым агрегатам `hop:N`, когда политика хранения сэмплы уже удалила. Смены
маршрута во втором случае не восстанавливаются: они живут в истории адресов, а её
в агрегатах нет. Список остаётся пустым — честнее, чем показать ноль смен там,
где их не по чему посчитать.

### `IHopAnnotator` — «у кого», а не только «где»

Список адресов отвечает на вопрос «где», но не на вопрос «у кого». Понимание, что потери
начинаются в транзите конкретного оператора, и есть то, ради чего трассировку показывают
провайдеру.

Порт объявлен в `Application`, реализация — в `Platform`. Обратный DNS работает всегда.
Номера автономных систем требуют офлайн-базы **DB-IP Lite** (CC BY-SA 4.0), которая
**не входит и не может входить в поставку**: её лицензия требует, чтобы производные
наследовали ту же лицензию, а это несовместимо с MIT нашего кода. Оператор кладёт файл
сам в `%LOCALAPPDATA%\StormMachine\geo`.

Это третья градация по зависимостям — после SNMP и захвата пакетов, и устроена так же:
без базы остаются адреса и имена, а отсутствие возможности **объясняется** строкой
с путём, а не прячется.

Читатель формата MMDB написан вручную (`Platform/Geo/MaxMindDatabase.cs`). Формат
маленький и полностью описан; сторонняя библиотека тянула бы чужую лицензию и чужие
обновления ради двух сотен строк разбора — то же решение и по той же причине, что
с разбором DNS в `DnsWire`. Оба читателя закрыты тестами на синтетических данных:
ошибка в них не падает, а тихо возвращает неверный ответ.

Результат обогащения публикуется через второй канал — факты категории `route`, где имя
факта есть адрес узла. Так таблица «адрес → чем известен» попадает в хранилище вместе
с прогоном и доживает до отчёта, не требуя повторных запросов в сеть.

### `MeasurementContext` — условия измерения

Сопровождает каждый результат: сетевой интерфейс и **его тип** (физический /
виртуальный / VPN / Wi-Fi), калибровочный базис, версия продукта, использованный бэкенд,
ссылка на методику (RFC). Без этого результаты несопоставимы между запусками
и бесполезны в отчёте.

### Обнаружение: кто как молчит

Порядок проб в `DiscoveryService` выбран не по удобству, а по тому, каким способом
узел отказывается отвечать.

| Проба | Кого находит | Кого нет |
|-------|--------------|----------|
| ICMP echo | всё, что отвечает на ping | рабочие станции Windows с брандмауэром |
| TCP к шести частым портам | закрывшихся от ICMP | тех, кто дропает и это |
| **таблица ARP после сканирования** | молчащих на всё | узлы за маршрутизатором |

Третья строка — главная. Узел может дропать любой трафик третьего уровня, но ответить
на ARP он обязан, иначе с ним нельзя разговаривать вовсе. Наши же пробы заставляют
систему выполнить разрешение адреса, и результат остаётся в таблице. На рабочей сети
так находится от пятой части до половины узлов.

Таблица читается **через паузу** после последнего пакета: ответы ARP ещё в пути,
и чтение сразу теряет половину улова. Полсекунды на трёх секундах работы — приемлемая
цена за узлы, которых иначе не видно вовсе.

Оттуда же берутся MAC-адреса: `SendARP` и `GetIpNetTable` работают **без прав
администратора и без драйвера захвата** (`R-03`). Это и делает инвентарь частью уровня 0.

### Инвентарь: устройство вычисляется, а не хранится

`Device` — не запись с полями, а результат слияния свидетельств. Всё, кроме адреса
и времён наблюдения, выводится правилом `EvidenceMerge`: правка оператора, затем вес
источника, затем свежесть, затем — сравнение самих значений ради устойчивости.
Последнее правило не про смысл, а про детерминизм: одни и те же свидетельства обязаны
давать один и тот же ответ независимо от порядка поступления, иначе повторное
сканирование меняло бы инвентарь произвольно и различия перестали бы что-либо значить.

**Тождество — MAC, и только иначе адрес.** В сети с DHCP адрес меняется; опознание
по адресу показало бы одно устройство как два, а различия между сканами — как
исчезновение и появление там, где ничего не происходило.

Отсюда следствие, которое пришлось доделывать после первого боевого сканирования:
у устройства **несколько адресов**, а не один. Маршрутизаторы, гипервизоры и хосты
с несколькими подсетями занимают их одним интерфейсом, и хранение единственного адреса
выглядело потерей — сканирование находило 75 адресов, инвентарь перечислял
74 устройства. Основной адрес выбирается как наименьший из известных, а не как
последний записанный: выбор обязан быть одинаковым при каждом пересчёте, иначе
различия между сканами зависели бы от порядка чтения.

### MAC говорит больше, чем вендор

Реестр IEEE отвечает на вопрос «кто выпустил», но у части адресов производителя нет
вовсе, и назвать такой адрес именем из реестра — сказать формально верное
и бесполезное. `MacAddresses` разбирает три случая:

| Адрес | Что показывает реестр | Что это на самом деле |
|-------|----------------------|----------------------|
| `00-00-5E-00-01-C8` | ICANN, IANA Department | VRRP, группа 200 — резервируемый шлюз |
| `2E-AF-19-F1-AF-E1` | ничего | локальный MAC: случайный адрес телефона или виртуальный адаптер |
| `00-11-32-E4-70-AA` | Synology | Synology |

Первая строка — тот случай, ради которого правило и появилось: увидев «ICANN», оператор
не узнаёт ничего, увидев «VRRP, группа 200» — узнаёт, что шлюз резервируется и что
групп на сети может быть несколько. Распознаются VRRP (RFC 5798), HSRP, HSRP v2
и GLBP. Решение принимает домен, показ только сокращает строку под ширину столбца.



Хранилище держит два представления, и это не дублирование:

| Представление | Что это | Меняется ли |
|---------------|---------|-------------|
| `scan_devices` | снимок: что именно было видно в тот раз | никогда |
| `devices` + `device_evidence` | сводный инвентарь: всё, что мы узнали | при каждом сканировании |

По снимкам считаются различия, поэтому переписывать их задним числом нельзя. В сводном
инвентаре живёт правка оператора — проверено тестом: устройство, названное человеком,
сохраняет имя после пересканирования, а снимок сохраняет наблюдённое.

### База OUI — третья градация по данным

Вендор по MAC входит в уровень 0, поэтому реестр IEEE **встроен в сборку** ресурсом
(53 тысячи записей, 540 КБ). Требовать ради него скачивания значило бы сломать сценарий
первого запуска, особенно в изолированной сети. Реестр публичный — в отличие от Npcap
(лицензия запрещает распространение) и DB-IP (CC BY-SA несовместима с MIT), которые
в поставку не входят и входить не могут.

Формат текстовый, по строке на запись: двоичный был бы на треть компактнее, но базу,
встроенную в поставку, должно быть видно на ревизии. Собирается скриптом
`tools/update-oui.cmd`, результат побайтово воспроизводим.

### `TopologyGraph` — карта как функция от свидетельств

Граф вычисляется, а не хранится, — то же устройство, что у инвентаря, и по той же
причине: повторное сканирование не должно затирать правку оператора. Пересчёт
детерминирован: узлы сортируются по виду и адресу, связи по концам, из совпавших
остаётся самая уверенная. Без этого «что изменилось» показывало бы перестановку.

Карта **своих измерений не делает**. Инвентарь дал устройства, сохранённые трассировки —
внешние пути, сетевое окружение — подсети; `TopologyService` их складывает. Отсюда
следует, что карта пересчитывается мгновенно и не трогает чужую сеть.

**Достоверность связи — часть модели, а не оформления.**

| `LinkConfidence` | Основание | Пример |
|------------------|-----------|--------|
| `Confirmed` | прямое свидетельство | ответ на ARP: протокол работает только внутри одного домена |
| `Inferred` | правило с исключениями | шлюз ведёт наружу; соседние хопы трассировки |
| `Assumed` | косвенный признак | адрес в диапазоне подсети без ответа на ARP |

У каждой связи есть строка `Because`. Она видна на экране и попадает в выгрузку:
догадка обязана себя объяснять, иначе её нельзя ни проверить, ни оспорить. Тест
`EveryInferredLink_ExplainsItself` следит, чтобы необъяснённых не появлялось.

Соседство хопов трассировки **никогда** не бывает `Confirmed` — прямое следствие И-7:
туннель MPLS без переноса TTL прячет участки пути, и цель отвечает с нескольких TTL.

Раскладка — MDS из MSAGL, рисование своё (`TopologyCanvas`). Ярусная раскладка на сети
даёт полотно 65 : 1 (спайк-04, `R-21`), а чужие стили не выражают различие
достоверности. Координаты в выгрузку JSON не входят: расположение узлов — свойство
показа, а не сети.

### `Evidence` — свидетельство о топологии

Узлы и связи не хранятся как правда — они **вычисляются** из набора свидетельств
(ARP, `SendARP`, SNMP, LLDP, FDB, mDNS, ping, OUI, traceroute, ручная правка).
Каждое несёт источник, время и уровень достоверности. Правка оператора — тоже
свидетельство, с наивысшим приоритетом и флагом `pinned`.

Пересчёт графа — **детерминированная функция** от набора свидетельств, а не мутация
состояния. Отсюда следует, что повторное сканирование не может затереть правку человека.

## 5. Горячий путь измерений

Отдельный режим кода со своими правилами:

- **Только собственный таймер** высокого разрешения. Значения RTT из системных API
  не используются никогда. Проверено: 191 различимое значение из 200 против единиц
  у целочисленного источника.
- **Бюджет аллокаций**, а не ноль. Полного нуля быть не может: системный API возвращает
  объект ответа на каждую пробу. Измерено 941 байт на пробу при бюджете 4096 и нуле
  сборок второго поколения. Считается `GC.GetTotalAllocatedBytes`, а **не**
  `GetAllocatedBytesForCurrentThread`: код асинхронный, продолжения идут на разных
  потоках пула, и потоковый счётчик показал бы неполную картину.
- **Калибровка**: порог разрешения измеряется на loopback при старте и **записывается
  в условия измерения, но не вычитается**. Путь через loopback — не чистые накладные
  расходы, там есть и собственная работа сетевого стека; вычитание давало бы
  систематическую ошибку и уводило бы быстрые каналы в минус.
- **Прогрев** асинхронного пути на loopback перед серией. Без него первые две пробы
  систематически завышены — на стенде 21.7 и 14.5 мс при реальных 0.5–0.7 мс.
  Прогрев идёт на loopback, а не на цель: лишние пакеты в измеряемую сеть не уходят.
- **Темповка пакетов** — гибридное ожидание: основную часть спим, последние 2 мс
  выбираем активным ожиданием. `Thread.Sleep` непригоден (спит вдвое дольше),
  `timeBeginPeriod` не помогает. Интервал отсчитывается от предыдущей **отправки**,
  а не от получения ответа, иначе темп «плывёт» вслед за задержкой сети.

## 6. Границы, подготовленные к server-варианту

`Application` не знает, кто его вызывает: GUI, CLI или (в будущем) HTTP-сервер.
Контракт между презентацией и приложением **сериализуем** — чтобы завтра стать сетевым.

`StormMachine.Cli` существует в том числе как доказательство этого свойства:
если консоль работает, значит ядро действительно не зависит от интерфейса.
