# Спайк-09 · Захват пакетов без драйвера и под обрезкой

**Вопросы.** Два, и второй важнее.

1. Переживает ли `SharpPcap` публикацию с `PublishTrimmed`? Вопрос тот же, что
   в спайках [06](../spike-06-scheduler/)–[08](../spike-08-snmp/), но острее:
   библиотека целиком построена на P/Invoke к `wpcap.dll`, а обрезчик про нативные
   вызовы рассуждать не умеет.
2. **Что происходит без установленного драйвера?** Npcap продукт не распространяет
   ни при каких условиях — лицензия NPSL это запрещает. Значит, у большинства
   пользователей драйвера не будет, и от того, *где* библиотека спотыкается — при
   загрузке сборки, при первом обращении к типу или при перечислении устройств, —
   зависит вся архитектура уровня 2.

Стенд для второго вопроса идеальный: на машине разработки Npcap не установлен.

## Результат

| Что проверяли | Без обрезки | После обрезки |
|---------------|-------------|---------------|
| Загрузка типа `CaptureDeviceList` | загружается | загружается |
| `CaptureDeviceList.Instance` без драйвера | `DllNotFoundException` | `DllNotFoundException` |
| `Pcap.Version` без драйвера | строка «pcap is not installed» — **без исключения** | то же |
| Предупреждения обрезчика | — | нет |

Публикация — один файл, поведение обеих сборок совпадает до буквы.

## Что из этого следует: динамическая загрузка плагина не нужна

Исходный план предполагал `plugins/` с **загрузкой во время работы**. Обоснование
было лицензионным: R-19 исследования гласит, что SharpPcap распространяется по LGPL-3.0,
а LGPL требует возможности подменить библиотеку — что несовместимо с обрезкой
и упаковкой в один файл.

**Предпосылка устарела.** SharpPcap 6.3.1 распространяется по **MIT** — это записано
в `<license type="expression">MIT</license>` его собственного nuspec. Требования
к перелинковке нет.

Остальные основания для динамической загрузки спайк тоже снял:

- типы поднимаются без драйвера — держать библиотеку в основном бинаре безопасно,
  экран возможностей не упадёт у того, у кого Npcap нет;
- обрезку библиотека переживает — выносить её из бандла незачем;
- отказ конкретен и опознаваем: `DllNotFoundException` ни с чем не спутать,
  а `Pcap.Version` вообще отвечает строкой и позволяет спросить о драйвере,
  ничего не роняя.

Динамическая загрузка добавила бы `AssemblyLoadContext` поверх однофайлового
обрезанного хоста — целый класс отказов ради нуля выгоды. **Решение: `plugins/` —
отдельная сборка и единственное место со ссылкой на SharpPcap, но подключается
она обычной ссылкой.** Условие приёмки И-18 выполняется структурой проектов,
а не механикой загрузки.

## Чем разбирать кадры

`PacketDotNet` 1.4.8 (MPL-2.0, приходит зависимостью SharpPcap) умеет из нужного нам:

- `LldpPacket` со всеми TLV: `ChassisIdTlv`, `PortIdTlv`, `SystemNameTlv`,
  `PortDescriptionTlv`, `ManagementAddressTlv`;
- `DhcpV4Packet` с типами сообщений и опциями — этого хватает, чтобы увидеть
  посторонний DHCP по ответам.

**CDP не поддержан** — его придётся разбирать самим: заголовок SNAP и простые TLV.
Это десятки строк, и они окупаются: сети, где выключен LLDP и включён CDP, встречаются.

## Запуск

```
dotnet run --project spikes/spike-09-capture/Spike09.csproj -c Debug          # база
dotnet publish spikes/spike-09-capture/Spike09.csproj -c Release -o <куда>    # обрезка
<куда>/spike09.exe
```

На машине с установленным Npcap второй шаг перечислит адаптеры вместо отказа —
это и будет проверкой второй половины уровня 2.
