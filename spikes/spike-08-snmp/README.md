# Спайк-08 · SharpSnmpLib под обрезкой

**Вопрос.** Переживает ли `Lextm.SharpSnmpLib` публикацию с `PublishTrimmed` —
и, отдельно, переживает ли её криптография SNMPv3?

**Почему спрашиваем.** Третий раз тот же вопрос ([06](../spike-06-scheduler/) — провал,
[07](../spike-07-velopack/) — успех), но здесь два новых повода для беспокойства.
Первый: разбор BER — рекурсивная фабрика типов, а такие в .NET часто устроены
на рефлексии. Второй, более острый: v3 считает HMAC и шифрует AES, а поиск алгоритма
по имени через `CryptoConfig` — классическая жертва обрезчика.

**Как проверяли.** Полный круг на опубликованном бинарнике (self-contained,
single-file, trimmed, 13.3 МБ):

1. Вывод ключа из пароля всеми четырьмя провайдерами проверки подлинности.
2. Шифрование и расшифровка AES с проверкой, что расшифрованное совпало с исходным.
3. `GET` и обход поддерева `ifDescr` против **устройства-дублёра**, поднятого тут же
   на 127.0.0.1: он разбирает запрос и собирает ответ той же библиотекой, так что
   обрезка проверяется на обеих половинах BER, а не только на чтении.

## Результат: проходит

| Что проверяли | Итог |
|---------------|------|
| `PasswordToKey` MD5 / SHA-1 / SHA-256 / SHA-512 | 16 / 20 / 32 / 64 байта |
| AES: шифрование → расшифровка | совпало с исходным |
| `GET` двух скалярных узлов | `sysDescr`, `sysName` прочитаны |
| Обход поддерева `1.3.6.1.2.1.2.2.1.2` | три интерфейса, обход остановился на границе поддерева |
| Предупреждения обрезчика (`TrimmerSingleWarn=false`) | нет |

Лицензия библиотеки — **MIT**, что и требуется: своя лицензия MIT, условия SignPath
и совместимость с будущим LGPL-плагином захвата.

## Побочный урок, ради которого стоит читать этот файл

С первого раза спайк **провалился дважды**: падало шифрование и возвращал пустоту обход
дерева. Соблазн был очевидный — записать это как «SharpSnmpLib не переживает обрезку»
и пойти искать замену, как было с Quartz.

Спасла привычка, которой в спайке-06 не было: **прогнать то же самое без обрезки.**
Необрезанная сборка провалилась ровно так же и в тех же двух местах — значит,
обрезчик ни при чём. Оба отказа оказались моими:

- `EngineIds` у провайдера шифрования не создан заранее, и обращение к нему давало
  `NullReferenceException` — библиотека здесь ни при чём;
- узлы дерева сортировались **как строки**, а строкой `14` меньше `2`. Дублёр отдавал
  соседа не из того поддерева, и обход честно останавливался на первом шаге. Настоящее
  оборудование отдаёт узлы в числовом порядке — дублёр обязан вести себя так же,
  иначе он проверяет не то.

Правило, стоящее записи: **у спайка должен быть базовый прогон без обрезки.** Без него
«не работает после обрезки» и «не работает вообще» неразличимы, а цена ошибки —
отвергнутая библиотека и написанная взамен своя. Ровно та цена, которую мы уже
однажды заплатили осознанно; платить её по недоразумению не стоит.

## Запуск

```
dotnet run --project spikes/spike-08-snmp/Spike08.csproj -c Debug          # база, без обрезки
dotnet publish spikes/spike-08-snmp/Spike08.csproj -c Release -o <куда>    # проверка обрезки
<куда>/spike08.exe
<куда>/spike08.exe 192.168.1.1 public                                      # против железа
```
